# Agent Loop 分层代理（目标-任务-执行 三层）模式

---

## 1. What（是什么）

**分层代理（Hierarchical Agent）** 是把单体 ReAct 循环按 **认知抽象层级** 纵向切开，形成 **三层独立但相互通信的 Agent Loop**：

```
┌──────────────────────────────────────────────────────────┐
│  L3  Goal Agent     —— "我要达成什么"  (Why / What)       │
│        ▲ 反馈：目标完成/失败/调整                          │
│        ▼ 下发：高层目标 + 约束 + 验收标准                  │
├──────────────────────────────────────────────────────────┤
│  L2  Task Agent     —— "我要做哪些事"  (Plan / Decompose) │
│        ▲ 反馈：任务结果 + 中间产物                         │
│        ▼ 下发：任务清单 / DAG / 单个 task spec             │
├──────────────────────────────────────────────────────────┤
│  L1  Execution Agent —— "我要怎么做"   (Act / Tool-Use)   │
│        ▲ 反馈：observation / artifact                     │
│        ▼ 下发：原子工具调用                                │
└──────────────────────────────────────────────────────────┘
```

| 层 | 别名 | 时间尺度 | 主要产物 | 典型 Prompt 角色 |
|---|---|---|---|---|
| **L3 Goal**（目标层） | Strategist / Meta-Planner / Manager | 分钟~小时 | 目标树、验收标准、预算 | "你是首席架构师" |
| **L2 Task**（任务层） | Planner / Orchestrator / Lead | 秒~分钟 | 任务 DAG、子任务规格 | "你是技术负责人，把目标拆成可执行 task" |
| **L1 Execution**（执行层） | Worker / Tool-User / ReAct Agent | 毫秒~秒 | tool_call / observation / 文件 | "你是工程师，调用工具完成 task" |

**核心特征**：
- **每层都是一个独立的 Agent Loop**（自己的 system prompt、上下文、停止条件）。
- **下层是上层的"工具"**：L3 调用 L2 就像调用一个函数；L2 调用 L1 也是。
- **信息在层间被压缩/解压**：上层只看摘要，下层只看与自己相关的局部。
- 与"单体 ReAct"相比，它牺牲一部分端到端连贯性，换来 **可扩展性、上下文隔离、可并行、可治理**。

> 它不是 ReAct 的替代品，而是 **ReAct 的"分形堆叠"**——每一层内部仍然是 Reasoning↔Acting 循环。

---

## 2. Why（为什么需要分层）

单体 ReAct 在任务规模变大后会遇到 **四堵墙**，分层是直接对策：

| 单体痛点 | 分层如何解决 |
|---|---|
| **上下文爆炸**：30+ 轮后 messages 撑爆窗口、注意力稀释 | 每层独立上下文，下层完成后只回传**摘要/产物**，上层窗口保持干净 |
| **目标漂移**：长链路里模型忘记初衷，被中间细节带偏 | L3 始终守着目标，每次评审 L2 结果时都重新对齐 |
| **无法并行**：单循环串行执行 | L2 可一次派发多个 L1 worker 并发执行（fan-out / map-reduce） |
| **难以治理**：权限、预算、安全策略全混在一个 prompt 里 | 分层天然就是**权限边界**：L1 才有工具权限、L2 才能花预算、L3 才能改目标 |
| **重试粒度粗**：失败一次要从头开始 | L1 失败 → L2 局部重试；L2 失败 → L3 重新规划；不必整体回滚 |
| **难以专业化** | 每层可用**不同模型**（L3 用强推理大模型 Opus/o1，L1 用便宜快模型 Haiku/4o-mini），显著降本 |

一句话：**分层 = 关注点分离（SoC）+ 抽象层级（Abstraction）在 Agent 架构上的应用**，本质上是软件工程"分层架构（OS Kernel / Compiler / Web 三层）"在 LLM 时代的复刻。

## 3. Who（谁在用 / 谁参与）

### 3.1 业界落地

| 系统 | 三层映射 |
|---|---|
| **Claude Code（Sub-agent 模式）** | Main Agent (L3+L2) → Task tool 派发 → Sub-agent (L1) |
| **Cursor Composer / Background Agents** | Planner → Editor → Apply/Tool |
| **Devin（Cognition）** | Planner → Executor → Shell/Browser/Editor |
| **MetaGPT** | Boss → PM/Architect/Engineer → Tool |
| **AutoGen GroupChat + Manager** | GroupChatManager → SpecializedAgent → FunctionCall |
| **OpenAI Swarm / Agents SDK** | Triage Agent → Specialist Agent → Tools |
| **LangGraph Supervisor 模式** | Supervisor Node → Worker Node → Tool Node |
| **HuggingGPT** | ChatGPT (Plan) → Model Selection → HF Model 执行 |

### 3.2 循环内角色

- **L3 Goal Agent**：通常 1 个，长生命周期，相当于"项目经理"。
- **L2 Task Agent**：1 个或多个（按领域切分，如"前端 Lead / 后端 Lead"）。
- **L1 Execution Agent**：可大量并发，**短生命周期、用完即弃（ephemeral）**，每个只看自己的 task spec。
- **共享基础设施**：消息总线 / Blackboard、Artifact Store（文件、向量库）、Trace 系统、预算/权限中心。
- **人类**：通常在 **L3 入口**（确认目标）和 **L2 关键决策点**（plan 审批）介入，不接触 L1。

## 4. When（什么时候用 / 什么时候别用）

### 4.1 适合

- **任务规模大**：预计 >30 步、>100k token、>5 分钟。
- **任务可分解**：存在天然的"目标—子任务—动作"层级（写一个完整 feature、跑一次数据分析、做一次安全审计）。
- **需要并行**：多个子任务无强依赖，能 fan-out。
- **需要治理**：要做权限隔离、预算控制、审计合规。
- **需要混合模型**：希望大模型只用在关键决策处，省钱。
- **需要可重入**：长任务要能 checkpoint、断点续跑。

### 4.2 不适合（过度设计）

- 简单问答 / 单步工具调用 → 直接 Function Call。
- 5~10 步以内的交互式编码小任务 → 单体 ReAct 更顺手、延迟更低。
- 任务拆不开 / 强串行依赖 → 分层只会增加沟通开销。
- 团队尚无 trace / 评测 / 沙箱基础设施 → 三层会让 bug 难定位。

**经验阈值**：当你的单体 ReAct 频繁出现 **"上下文超限 / 目标漂移 / 想并行但不能"** 三者中任意一个时，就该上分层。

## 5. Where（在系统中的位置）

```
┌─────────────────────────────────────────────────────────────────┐
│                       Host (CLI / IDE / Server)                  │
│                                                                  │
│   ┌──────────── L3 Goal Loop ────────────┐                      │
│   │  state: GoalTree, AcceptanceCriteria │                      │
│   │  tools: [spawn_task_agent, ask_user, │                      │
│   │          revise_goal, finalize]      │                      │
│   └──────────────────┬───────────────────┘                      │
│                      │ TaskSpec / Plan 请求                      │
│                      ▼                                           │
│   ┌──────────── L2 Task Loop ────────────┐                      │
│   │  state: TaskDAG, Progress, Budget    │                      │
│   │  tools: [decompose, spawn_worker,    │                      │
│   │          merge_results, replan]      │                      │
│   └──────────────────┬───────────────────┘                      │
│                      │ 多个 Worker 并发                          │
│         ┌────────────┼────────────┐                              │
│         ▼            ▼            ▼                              │
│   ┌──L1──┐      ┌──L1──┐     ┌──L1──┐                           │
│   │ReAct │      │ReAct │     │ReAct │   (每个独立上下文)         │
│   └──┬───┘      └──┬───┘     └──┬───┘                           │
│      ▼              ▼              ▼                             │
│   ┌──────────────────────────────────────┐                       │
│   │ Shared Layer:                        │                       │
│   │   • Tool Sandbox (FS/Shell/HTTP)     │                       │
│   │   • Artifact Store (files, vectors)  │                       │
│   │   • Message Bus / Blackboard         │                       │
│   │   • Budget & Permission Broker       │                       │
│   │   • Tracing (OTel / Langfuse)        │                       │
│   └──────────────────────────────────────┘                       │
└─────────────────────────────────────────────────────────────────┘
```

**关键位置原则**：
- **工具执行权下沉到 L1**：L3/L2 不直接碰 shell / fs，只通过派发 worker。
- **状态上提**：所有可被审计/恢复的状态（GoalTree、TaskDAG、Artifacts）由宿主集中存储，不锁在某个 Loop 内存里。
- **跨层通信走结构化协议**（JSON Schema / Protobuf），而不是自由文本，便于 trace 和回放。

## 6. How（怎么做 —— 实现要点）

### 6.1 三层各自的循环模板

**L3 Goal Loop**（频率最低、token 最贵、模型最强）

```python
while not goal.is_satisfied():
    state = summarize(goal_tree, completed_tasks, artifacts)
    decision = LLM_strong(system=GOAL_PROMPT, context=state)
    # decision ∈ {spawn_task, revise_goal, ask_user, finalize}
    if decision.type == "spawn_task":
        result = run_task_agent(decision.task_spec)   # 阻塞或异步
        goal_tree.update(result.summary)              # 只吃摘要
    elif decision.type == "finalize":
        return decision.final_answer
```

**L2 Task Loop**（中频、负责拆解与编排）

```python
while task_dag.has_pending():
    ready_tasks = task_dag.ready_nodes()              # 取无依赖的子任务
    # 关键：可批量并发派发
    results = parallel_map(run_worker, ready_tasks, max_workers=N)
    for r in results:
        task_dag.mark(r.task_id, r.status, r.artifact_ref)
        if r.status == "failed":
            replan_decision = LLM_mid(REPLAN_PROMPT, r)   # 局部重规划
            task_dag.apply(replan_decision)
return summarize_to_goal_layer(task_dag)
```

**L1 Execution Loop**（高频、ReAct、可便宜模型）

```python
def run_worker(task_spec):
    messages = [SYSTEM_WORKER, task_spec.as_prompt()]
    for _ in range(task_spec.max_steps):              # 由上层卡预算
        resp = LLM_cheap(messages, tools=task_spec.allowed_tools)
        messages.append(resp.message)
        if not resp.tool_calls:
            return WorkerResult(ok=True,
                                summary=resp.content,
                                artifact=collect_artifacts())
        for call in resp.tool_calls:
            obs = sandbox.execute(call, perms=task_spec.perms)
            messages.append(tool_msg(call.id, truncate(obs)))
    return WorkerResult(ok=False, reason="max_steps")
```

### 6.2 跨层契约（最容易翻车的地方）

每次"上→下"派发，必须是一份**结构化 TaskSpec**，至少包含：

```jsonc
{
  "id": "task-7f3",
  "parent_goal": "实现用户登录",
  "description": "在 src/auth/login.ts 实现 POST /login，参数 ...",
  "inputs": { "design_doc": "artifact://doc-12" },
  "deliverables": ["修改后的文件列表", "通过的单测"],
  "acceptance_criteria": ["npm test 通过", "覆盖率 >80%"],
  "allowed_tools": ["read_file", "write_file", "shell:npm test"],
  "permissions": { "fs_write": ["src/auth/**"], "network": false },
  "budget": { "max_steps": 20, "max_tokens": 30000, "max_seconds": 120 },
  "model_hint": "claude-haiku"
}
```

每次"下→上"回报，必须是一份**结构化 Result**：

```jsonc
{
  "task_id": "task-7f3",
  "status": "ok | failed | needs_help",
  "summary": "已实现登录接口，3 个单测通过",
  "artifacts": ["artifact://diff-88"],
  "metrics": { "steps": 12, "tokens": 18400, "cost_usd": 0.04 },
  "open_questions": []
}
```

> **黄金法则：上层不读下层的 raw messages，只读 summary + artifacts ref**。这是上下文不爆炸的根本保证。

### 6.3 关键工程模式

| 模式 | 作用 |
|---|---|
| **Plan-and-Execute** | L2 先一次性出 DAG，再交给 L1 执行；适合任务可静态拆解的场景。 |
| **Recursive Decomposition** | L1 发现任务过大时，可"反向请求 L2 进一步拆"，形成递归（要设递归深度上限）。 |
| **Critic / Verifier** | 在 L2 层挂一个独立 critic agent，对 worker 结果二次检查后再回报 L3。 |
| **Blackboard 共享内存** | 多个 L1 worker 通过共享的 KV/向量库交换中间产物，避免 L2 当中转瓶颈。 |
| **Checkpoint & Resume** | L3/L2 状态序列化到磁盘，崩溃后可从最近 checkpoint 续跑（Devin 长任务做法）。 |
| **Budget Broker** | 全局预算服务，每次 spawn 子 agent 都要先"申领额度"，防止失控。 |
| **Permission Broker** | 工具调用前查 task_spec.permissions，越权直接拒绝。 |
| **Replan on Failure** | L1 失败 N 次，L2 触发局部重规划；L2 整体失败，L3 决定降级 / 改目标 / 求助人。 |
| **Human-in-the-loop Gate** | 在 L3→L2 之间插入"plan 审批门"，在 L2→L1 之间插入"高危操作确认门"。 |

### 6.4 反模式（容易踩的坑）

1. **三层共享同一份 messages** —— 等于没分层，上下文照样爆。
2. **L3 直接调 shell** —— 破坏分层，权限治理失效。
3. **下层把全部 raw 日志回灌上层** —— 上下文压缩没做，分层收益归零。
4. **递归无深度限制** —— L1 反复请求拆解，形成"无限规划循环"，烧钱。
5. **三层都用 GPT-4 级大模型** —— 成本爆炸，没拿到分层最大红利（差异化模型）。
6. **跨层用自由文本传参** —— 解析脆弱、无法 trace；必须结构化 schema。
7. **没有全局 trace_id 串起三层** —— 出问题时根本不知道哪条链路炸的。

## 7. How much（成本与规模）

### 7.1 性能与规模量级（编码 Agent 经验值）

| 维度 | 单体 ReAct | 三层分层 |
|---|---|---|
| **可承载任务规模** | 10~50 步 | 100~1000+ 步 |
| **典型 token 消耗** | 50k~300k | 200k~2M（但分散在多 worker） |
| **单次延迟** | 1~5 分钟 | 5~30 分钟（端到端），但因并行，**等价工作量**可缩短 30~70% |
| **基准提升** | baseline | SWE-bench / GAIA 通常再 +10~25 分 |
| **失败粒度** | 全部回滚 | 局部重试，恢复成本 ↓ 60%+ |

### 7.2 成本结构与优化

**成本来源**：
1. **跨层通信开销**：每次 spawn 都有 system prompt + schema 的固定 overhead（每个 worker 通常多花 2~5k token）。
2. **重复阅读 artifact**：worker 之间共享文件时，若都全文读，token 翻倍。
3. **Critic / Verifier**：增加一轮 LLM 调用，约 +15~30% token。

**省钱杠杆**（这是分层最大魅力）：
- **模型分级**：L3 用 Opus/o1（占总调用 <5%），L2 用 Sonnet/4o，L1 用 Haiku/4o-mini（占 >80% 调用）。实测**总成本可降 40~70%**，质量损失 <5%。
- **并行换时间**：worker 并发不省钱但省墙钟时间，对交互式产品体验提升巨大。
- **artifact 引用代替全文**：worker 间传 `artifact://id` + 摘要，按需懒加载。
- **缓存 system prompt**：L1 worker 模板 prompt 用 prompt caching（Anthropic / OpenAI 都支持），命中率常 >90%。

### 7.3 工程与运维成本

| 项 | 成本 |
|---|---|
| **初始搭建** | 中等：需要消息协议、artifact store、trace、预算 broker，约 2~6 人周。 |
| **调试难度** | **显著高于单体**：必须有完整分布式 trace（OpenTelemetry + Langfuse / Phoenix），否则定位问题极痛苦。 |
| **评测难度** | 需要分层评测：L3 看目标达成率，L2 看 plan 质量 & 任务成功率，L1 看 tool 成功率 & 步数效率。 |
| **运维风险** | 失控的 spawn 是头号事故源 → 必须有 **全局并发上限 + 预算硬熔断 + 递归深度限制** 三道闸。 |

---

## 一句话总结

> **分层代理（Goal-Task-Execution）= 把"一个大循环"拆成"三个互相调用的小循环"，用结构化契约和摘要传递在层间隔离上下文，用模型分级和并行 fan-out 换取规模与成本优势。它是单体 ReAct 撞到上下文墙、目标漂移墙、并行墙之后的标准下一站，也是 Devin / Claude Code Sub-agent / MetaGPT 等"长任务 Agent"的事实架构基线——代价是更复杂的工程基础设施和更高的调试门槛。**
