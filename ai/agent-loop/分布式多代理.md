# Agent Loop 分布式多代理（多角色协作）模式 

---

## 1. What（是什么）

**分布式多代理（Distributed Multi-Agent / Role-based Collaboration）** 是把任务**横向**切分给**多个平级、具有不同角色与专长的 Agent**，它们通过**显式通信协议**协作完成目标。与"分层"的纵向抽象不同，它强调的是**横向分工与对话**。

**最小心智模型**：

```
          ┌─────────────────────────────────────────┐
          │           Shared Environment             │
          │  (Blackboard / MessageBus / Artifacts)   │
          └───┬──────────┬──────────┬──────────┬────┘
              │          │          │          │
          ┌───▼───┐  ┌───▼───┐  ┌───▼───┐  ┌──▼────┐
          │Agent A│  │Agent B│  │Agent C│  │Agent D│
          │ (PM)  │⇄ │(Arch) │⇄ │ (Dev) │⇄ │ (QA)  │
          └───────┘  └───────┘  └───────┘  └───────┘
           每个 Agent 内部 = 一个独立 ReAct/分层 Loop
```

**关键定义要素**（缺一就不算"分布式多代理"）：

| 要素 | 含义 |
|---|---|
| **多实例** | ≥2 个独立运行的 Agent，各自有独立上下文、独立 LLM 调用、独立生命周期 |
| **角色化（Role）** | 每个 Agent 有**明确 persona + 专长 + 工具权限**（PM / Architect / Coder / Reviewer / Researcher...） |
| **显式协议通信** | 走**结构化消息**（tool-call / A2A / FIPA-ACL / 自定义 JSON），而不是共享一份 messages |
| **协作拓扑** | 存在一种编排形态：GroupChat / Supervisor / Pipeline / Debate / Swarm / Market |
| **涌现性** | 任务结果由**多 agent 交互**产生，不是任何单一 agent 独立完成 |

**与"分层代理"的本质区别**：

| 维度 | 分层（Hierarchical） | 分布式多代理（Multi-Agent） |
|---|---|---|
| 切分方向 | **纵向**（抽象层级） | **横向**（角色/专业分工） |
| Agent 关系 | 上下级（调用-被调用） | **平级**（对话-协商） |
| 通信 | 父→子派发 + 子→父汇报 | 多对多消息 / 广播 / 订阅 |
| 决策 | 上层集中决策 | **去中心化 / 协商涌现** |
| 类比 | 函数调用栈 | 团队会议 / 微服务 |

> 现实中二者常**混合**：一个 Supervisor（L3 分层思维）下挂多个平级专家 Agent（多角色思维）—— 这是当前最主流的工业形态。

## 2. Why（为什么用）

### 2.1 认知与能力维度

| 动机 | 解释 |
|---|---|
| **专业化分工（Specialization）** | 单个通用 Agent prompt 越堆越臃肿，能力反而下降；拆成专精角色（每个只吃自己那份 system prompt + 工具），各自更锐利。 |
| **视角多样性（Diversity → Robustness）** | 多 agent 辩论 / 交叉评审能显著减少幻觉和盲区（Debate / Society of Mind / Constitutional AI 的思路）。实证：多 agent 在推理基准上普遍 +5~15 分。 |
| **认知负载分散** | 每个 agent 只维护自己关心的上下文，避免"什么都要记"的认知过载。 |
| **涌现协作** | 复杂问题在交互中**自组织**出解法，而非预先编程（MetaGPT / ChatDev / Generative Agents 的核心卖点）。 |

### 2.2 工程与业务维度

| 动机 | 解释 |
|---|---|
| **组织同构（Conway's Law）** | 现实团队就是多角色协作，Agent 团队直接映射真实研发/运营组织，易被业务接受。 |
| **独立部署与伸缩** | 每个角色可独立服务化、独立 scale、独立灰度发布（像微服务）。 |
| **异构模型 / 异构厂商** | PM 用 Claude、Coder 用 GPT、Reviewer 用本地开源模型，按角色挑最合适的。 |
| **故障隔离** | 某个 agent 崩溃/超时，其余 agent 可继续或补位，不像单体一挂全挂。 |
| **跨组织协作（A2A）** | 不同公司/系统的 Agent 可基于开放协议（如 Google A2A、MCP + Agent Card）互操作。 |
| **可治理与审计** | 每个 agent 的输入输出都是结构化消息，天然形成审计日志。 |

### 2.3 何时"必须"分布式（不是可选而是必需）

- 任务涉及**强异构工具链**（代码 / 设计 / 数据 / 法务），单 agent 的 tool 列表已超过 ~50 个。
- 需要**对抗性验证**（红队 vs 蓝队、辩论双方、Critic vs Actor）。
- 需要**跨信任域协作**（不同公司的 agent、不同权限的部门 agent）。
- 需要**7x24 长驻 + 事件驱动**（每个 agent 订阅自己关心的事件，而不是一个主循环轮询）。

## 3. Who（谁在用 / 谁参与）

### 3.1 业界代表系统

| 系统 | 拓扑 | 代表角色 |
|---|---|---|
| **MetaGPT** | Pipeline + GroupChat | Boss → PM → Architect → PM → Engineer → QA |
| **ChatDev** | Waterfall Pipeline | CEO / CTO / Programmer / Reviewer / Tester |
| **AutoGen (Microsoft)** | GroupChat + Manager | 任意自定义角色，支持代码执行 agent |
| **CrewAI** | Crew + Tasks | 声明式角色 + 任务，面向工程落地 |
| **OpenAI Swarm / Agents SDK** | Handoff（角色交接） | 以"Agent 转交"为核心原语 |
| **LangGraph Multi-Agent** | 有向图 / Supervisor | 节点即 Agent，边即消息路由 |
| **Camel-AI** | Role-Playing Dialogue | User Agent ↔ Assistant Agent 双人对话 |
| **Generative Agents (Stanford)** | Simulation Society | 25 个村民 agent，记忆/反思/规划 |
| **Google A2A Protocol** | 开放互操作 | 跨厂商 agent 互发消息的标准 |
| **Anthropic MCP + Agent Card** | 工具/能力发现 | Agent 通过 Card 暴露能力，互相发现调用 |

### 3.2 参与者（循环之外也要算上）

- **Agent 群**：多个角色化 LLM Loop。
- **Orchestrator / Router / Manager**：决定"下一个该谁说 / 谁做"——可以是规则、可以是另一个 LLM、也可以是选举/拍卖。
- **Shared Environment**：Blackboard、Message Bus（Kafka / NATS / Redis Streams）、Artifact Store、Vector Memory。
- **Protocol Layer**：消息 schema、能力发现（Agent Card）、寻址（Agent URI）、安全（签名、鉴权）。
- **Human**：在关键节点作为一个"特殊 agent"加入（HITL）。
- **Observability Stack**：分布式 tracing 必备（OTel / Langfuse / Phoenix / LangSmith）。

## 4. When（什么时候用 / 什么时候别用）

### 4.1 适合

- 任务可**按角色/专业**自然切分（软件研发、内容创作、科研、金融分析、客服分诊）。
- 需要**多视角交叉验证**（医疗多专家会诊、法律多方论证、代码多角色评审）。
- 流程**长、异步、事件驱动**（运营自动化、7x24 监控处置）。
- 需要**跨组织 / 跨系统**协作（B2B agent 互操作）。
- **仿真与社会实验**（多 agent 经济体、策略博弈）。

### 4.2 别用（典型过度设计）

- 一个人类工程师 10 分钟能完成的小任务 → 单体 ReAct 足矣。
- 任务本质串行 + 单专业 → 多 agent 只会增加通信开销和"议而不决"。
- 团队没有**分布式 trace 和消息总线**基础设施 → 调试地狱。
- 预算敏感的高频短任务 → 多 agent 的 token 开销常是单体的 3~10 倍。
- 对**延迟**极敏感（单次 <3s）→ 多轮对话轮次撑不起 SLA。

### 4.3 决策口诀

> **"一个人想不明白 → 用分层；一群人要开会 → 用多代理；既想不明白又要开会 → 分层+多代理混合。"**

## 6. How（怎么做 —— 实现要点）

### 6.1 消息协议（生死线，必须结构化）

最小可用消息 schema：

```jsonc
{
  "msg_id": "m-1a2b",
  "conversation_id": "conv-42",
  "trace_id": "trace-xyz",            // ← 串联所有 agent 的 trace
  "sender": "agent://dev-1",
  "recipients": ["agent://qa-1"],     // 可多播 / 可广播 *
  "role": "assistant",                // assistant / tool / system / human
  "intent": "request_review",         // propose / critique / handoff / ask / inform / commit
  "content": { ... },                 // 结构化业务负载
  "artifacts": ["artifact://diff-88"],
  "reply_to": "m-09ab",
  "created_at": "...",
  "signature": "..."                  // 跨信任域时必需
}
```

**必备字段**：`trace_id`（跨 agent 追踪）、`intent`（语义明确）、`artifacts`（大对象引用而非内联）。

### 6.2 Agent 定义模板

```python
@dataclass
class AgentSpec:
    name: str
    role: str                    # "Architect" / "Coder" / "Reviewer"
    system_prompt: str           # 角色人设 + 职责 + 协作准则
    model: str                   # 可异构
    tools: list[Tool]            # 该角色专属工具
    permissions: Permissions     # fs/net/budget
    memory: MemoryBackend        # 私有记忆 + 对共享 blackboard 的订阅
    inbox_filter: Callable       # 决定哪些消息要处理
    max_turns_per_task: int
```

### 6.3 单个 Agent 的内部循环（事件驱动版）

```python
async def agent_runtime(spec: AgentSpec, bus: MessageBus):
    while True:
        msg = await bus.next(spec.inbox_filter)         # 阻塞等消息
        ctx = spec.memory.load(msg.conversation_id)
        ctx.append(msg)
        # 内部仍是 ReAct / 分层循环
        reply = await react_loop(spec, ctx)
        spec.memory.save(ctx)
        if reply:
            await bus.publish(reply)                    # 产出消息（给某人/广播）
        if is_terminal(reply):
            await bus.publish(done_event(msg.conversation_id, spec.name))
```

### 6.4 编排器核心算法（Who-Speaks-Next）

这是多代理系统的**灵魂**，四类主流实现：

1. **Rule-based（最稳，调试友好）**
   ```python
   ORDER = ["PM", "Architect", "Coder", "QA"]
   next_agent = ORDER[(turn) % len(ORDER)]
   ```
2. **LLM-as-Router（灵活，AutoGen GroupChat 默认）**
   让一个"Manager LLM"看当前对话摘要，输出下一个 speaker 名字。
3. **Handoff / Transfer（OpenAI Swarm）**
   当前 agent 显式调用 `transfer_to(agent_name)` 工具移交控制权。
4. **Market / Auction（去中心化）**
   任务广播，每个 agent 报价（置信度/成本），编排器选最佳。

### 6.5 终止与防死锁（极易翻车）

多代理的"不会停"是头号事故。必设：

| 机制 | 实现 |
|---|---|
| **全局轮次上限** | `max_rounds` 一到强制收敛，由 Judge agent 出终结答案 |
| **无进展检测** | 连续 N 轮 embedding 相似度 > θ → 判定卡死 → 触发打破机制 |
| **预算熔断** | 总 token / 费用 / 墙钟超限 → 强制结束 |
| **环路检测** | A→B→A→B 同话题 >k 次 → 强行 handoff 给 Judge |
| **显式 COMMIT 语义** | 只有特定 intent=`commit`/`finalize` 才能结束会话 |
| **人类兜底** | 触发异常时把 conversation 升级给 human agent |

### 6.6 一致性与并发（分布式的老问题回来了）

多 agent 并发写同一文件/状态时，必须处理：

- **乐观锁 / CAS**：artifact 带版本号，冲突时重试。
- **事务边界**：定义"一个协作会话"的 ACID 边界（通常用 Saga 补偿模式）。
- **幂等消息**：`msg_id` + 幂等键，消息可能重投。
- **因果一致（Causal Consistency）**：`reply_to` + 向量时钟，避免"先看到回复再看到问题"。
- **共享 Blackboard 的读写策略**：谁能写 / 谁只读 / 如何订阅变更。

### 6.7 安全与信任（跨域必修）

- **身份与鉴权**：每个 agent 有 DID / 证书，消息签名。
- **权限隔离**：工具调用走 broker，按 agent 身份授权。
- **Prompt Injection 防线**：收到外部 agent 的消息视为**不可信输入**，不能直接塞进 system prompt。
- **能力发现**：Agent Card（类似 OpenAPI for agents），声明能做什么、吃什么、产什么。
- **审计留痕**：所有跨 agent 消息不可篡改落盘（WORM）。

### 6.8 九大反模式

1. **共享一份 messages 列表** —— 退化成单体 ReAct。
2. **所有 agent 同 prompt 只换名字** —— 没有真正专业化，纯粹烧 token。
3. **无编排器的自由群聊** —— 不是涌现，是灾难，必死循环。
4. **Manager 用弱模型** —— 调度错一步，全员空转。
5. **消息走自由自然语言** —— 解析脆弱，trace 断裂。
6. **大 artifact 塞进消息体** —— 立刻爆 token，必须走引用。
7. **没有 trace_id 贯穿** —— 出事故查不出是哪个 agent。
8. **无预算全局视图** —— 某 agent 死循环烧爆账户。
9. **人类按钮长期按着不放** —— 每步都要人确认 = 退化成人类在开会。

## 7. How much（成本、规模、收益）

### 7.1 规模量级

| 指标 | 典型范围 | 备注 |
|---|---|---|
| Agent 数量 | 3~10（工程系统）；50~1000（仿真） | 生产系统超过 ~15 基本意味着该重构为分层+集群 |
| 协作轮次 | 10~100 轮/会话 | >100 通常是没收敛，需排查 |
| 并发任务 | 单 host 可撑 100~1000 会话 | 瓶颈在 LLM QPS 和消息总线 |
| 端到端延迟 | 分钟级~小时级 | 不适合强实时交互 |

### 7.2 Token / 费用模型（经验公式）

```
Total_tokens ≈ Σ_agents (system_prompt + private_context + incoming_msgs + own_output) × turns
            ≈ k · N_agents · avg_turns · avg_ctx_per_turn
```

常见**放大倍数**（相对单体 ReAct 做等价任务）：

| 任务类型 | Token 放大 | 成本放大 | 质量提升 |
|---|---|---|---|
| 代码开发（MetaGPT 类） | ×3~5 | ×2~4（模型分级后） | +10~25% 通过率 |
| 多角色辩论 | ×2~3 | ×1.5~2.5 | +5~15 分（推理基准） |
| 仿真社会 | ×10~100 | ×10~100 | 非功能性价值（研究用途） |

### 7.3 省钱与提效杠杆

- **模型分级**：Manager/Judge 用强模型（占调用 <10%），Worker 角色用中小模型。**常省 40~60%**。
- **Prompt Caching**：每个角色的 system prompt 巨长但稳定 → 缓存命中率 >95%。
- **消息摘要**：长对话按滑窗 + 摘要压缩，只给每个 agent 它关心的部分。
- **并行角色**：无依赖的角色（如多个 reviewer）并发跑，省墙钟不省钱。
- **早停**：Judge 判定已达成 → 立刻终止剩余 agent，别让流水线跑完。
- **精简角色**：生产系统经验，**3~5 个强角色 >> 10 个模糊角色**，后者沟通开销反而拖垮质量。

### 7.4 工程与运维成本（诚实评估）

| 项 | 评估 |
|---|---|
| 初始搭建 | **高**：消息总线 + 协议 + 编排器 + 分布式 trace + 预算 broker，3~8 人周起。 |
| 调试难度 | **很高**：必须有消息级 replay、对话可视化（类似 Langfuse Sessions / AutoGen Studio）。 |
| 评测难度 | **高**：既要评单 agent 质量，又要评协作质量（协同效率、冗余度、收敛速度）。 |
| 稳定性风险 | **高**：死锁 / 环路 / 预算爆炸是常见事故；必须全链路熔断 + 金丝雀。 |
| 组织成本 | 通常需要一个"Agent 架构师"角色长期维护角色定义与协作协议。 |

### 7.5 ROI 判断经验值

- 任务规模 **< 20 步**：多代理通常**负收益**。
- 20~100 步 + 可分工：多代理 **+10~25% 质量**，代价 2~3× 成本，**通常值得**。
- > 100 步 + 多专业：分层 + 多代理混合架构**几乎是唯一可行解**。
- 仿真/研究场景：不以 ROI 衡量，看涌现价值。

## 一句话总结

> **分布式多代理（多角色协作）= 用一组专业化、平级、通过结构化消息对话的 Agent，在共享环境中协同解决单个 Agent 无法独立承担的复杂任务。它的核心红利是"专业化 + 多视角 + 可治理 + 可伸缩"，核心代价是"通信开销 + 编排复杂度 + 调试难度 + token 放大"。它不是单体 ReAct 的升级版，而是当任务触及"多专业、多视角、多信任域、长流程、事件驱动"任意一条时的必然架构选择；在工业实践中，最稳的形态是"Supervisor 编排 + 3~5 个强角色 + 严格协议 + 全链路 trace + 硬熔断"，并常与分层代理组合使用。**
