# Agent Loop 单体循环（ReAct 式推理-行动交错）—— 5W2H 详解

---

## 1. What（是什么）

**Agent Loop 单体循环**指：单个 Agent 进程内部，以一个**主循环**驱动 LLM 不断进行 **Reasoning（思考）→ Acting（调用工具）→ Observing（获取结果）→ Reasoning（再思考）** 的迭代过程，直至模型自行决定输出 **Final Answer** 或满足终止条件。

它源自 **ReAct 论文**（Yao et al., 2022, *ReAct: Synergizing Reasoning and Acting in Language Models*），核心是把"思维链 CoT"和"工具调用 Tool-Use"**交错（interleave）**在同一条上下文里，而不是先想完再做、或先做完再想。

一次循环（一个 turn）的最小三元组：

```
Thought_i  →  Action_i  →  Observation_i
```

伪代码：

```python
context = [system_prompt, user_query]
while True:
    response = LLM(context)            # ① Reasoning（产出 Thought + Action）
    if response.is_final_answer:
        return response.text           # ④ 终止
    obs = execute_tool(response.action)# ② Acting + ③ Observing
    context += [response, obs]         # 把观测拼回上下文，进入下一轮
```

**"单体（Monolithic）"** 的含义：所有推理、决策、工具编排都在**同一个 LLM 上下文 + 同一个调度循环**内完成，**没有**子 Agent、没有多角色协作、没有外部工作流引擎。与之对应的反面是 **Multi-Agent / Orchestrator-Worker / Graph-based** 架构。

---

## 2. Why（为什么用它）

| 动机 | 说明 |
|---|---|
| **推理与行动相互校正** | 纯 CoT 容易"幻觉链路"；纯 Tool-Use 缺乏规划。交错后，工具的真实 Observation 可以**及时纠偏**下一步思考。 |
| **实现极简** | 只有一个 while 循环 + 一个 LLM + 一组 tools，无需编排框架，调试、复现、回放都容易。 |
| **上下文连续** | 全程共享一份 messages，模型对历史决策有完整记忆，便于回溯和反思（Reflexion / Self-Critique 容易插入）。 |
| **天然适配 Function Calling** | OpenAI / Anthropic / Qwen 等原生 tool_use 协议就是为这种循环设计的，落地成本低。 |
| **可解释性强** | 每一步 Thought 都是自然语言，便于审计和 Trace。 |

**代价（也是 Why-Not）**：上下文随轮次线性膨胀、长任务易"漂移"、串行执行无法并行、单点 LLM 决策瓶颈。

---

## 3. Who（谁在用 / 谁参与）

- **典型产品 / 框架**
  - **Claude Code、Cursor Agent、Codex CLI、Gemini CLI** —— 编码 Agent 几乎都是单体 ReAct 循环。
  - **LangChain `AgentExecutor`（ReAct Agent）**、**LlamaIndex ReActAgent**、**AutoGPT 早期版本**、**Qwen-Agent**、**OpenAI Assistants API（Run 循环）**。
- **循环内的角色**
  - **LLM**：推理者 + 决策者（选哪个 tool、传什么参数、何时停止）。
  - **Tool Executor / Sandbox**：执行 shell、读写文件、HTTP、检索、代码运行等。
  - **Loop Controller（宿主程序）**：拼装 prompt、解析 tool_call、调度执行、注入 observation、判停。
  - **用户**：可在中途被请求确认（Human-in-the-loop）。

---

## 4. When（什么时候用）

**适合**：

- 任务**步骤数中等（几步到几十步）**、路径**事先不确定**、需要根据中间结果动态决策。
- 工具集**相对收敛**（10~50 个量级），单个 LLM 上下文塞得下描述。
- 需要**强可解释、可中断、可人工接管**的交互式场景（IDE Agent、运维助手、研究助手）。

**不适合**（应改用其他形态）：

- 步骤极多 / 上下文将爆炸 → 需要 **Compaction / Sub-agent / 分层规划**。
- 多个子任务可**并行** → 需要 **Multi-Agent / Fan-out**。
- 流程**高度结构化、可静态编排** → 用 **Workflow / DAG（如 LangGraph 静态图）** 更稳更省。
- 严格 SLA、低延迟单跳问答 → 直接 RAG 或单次 Function Call 即可，不必引入循环。

```
┌────────────────────────────────────────────────────────┐
│                     Host Application                    │
│  (CLI / IDE Plugin / Web Server / Chat UI)              │
│                                                         │
│   ┌──────────────── Agent Loop ────────────────┐       │
│   │  while not done:                            │       │
│   │     ├─► LLM (Reasoning)  ◄── messages[]    │       │
│   │     ├─► Parse tool_call                     │       │
│   │     ├─► Tool Executor  ──► Sandbox/API     │       │
│   │     └─► Append Observation                  │       │
│   └─────────────────────────────────────────────┘       │
│                       │                                 │
│           ┌───────────┼────────────┐                    │
│           ▼           ▼            ▼                    │
│        Tools       Memory      Tracing/Log              │
│      (FS/Shell/   (KV/Vec)    (OTel/Langfuse)           │
│       HTTP/RAG)                                         │
└────────────────────────────────────────────────────────┘
```

位置特征：**Loop 是宿主进程的一个内嵌组件**，上接 UI/CLI，下接 Tools 与 LLM Provider，旁挂 Memory 与 Observability。

## 6. How（怎么做 —— 实现要点）

### 6.1 一轮的标准流程

1. **构造 messages**：`system + tools_schema + user + 历史 (assistant tool_calls / tool results)`。
2. **调用 LLM**（开启 function calling / tool use）。
3. **判停**：若返回纯文本且无 tool_call → Final Answer，跳出。
4. **执行工具**：解析 `tool_calls[]`，可串行或并行调用；捕获异常。
5. **回填 Observation**：以 `role: tool` / `tool_result` 形式追加到 messages。
6. **回到 1**。

### 6.2 Prompt 范式（经典 ReAct 文本式）

```
Thought: 我需要先列出当前目录文件
Action: shell
Action Input: {"cmd": "ls -la"}
Observation: total 24  drwxr-xr-x  ...
Thought: 看到 package.json，下一步读取它
Action: read_file
...
Thought: 信息足够了
Final Answer: 这是一个 React 项目，依赖 ...
```

> 现代实现已基本用 **原生 tool_use 协议**取代上面的纯文本格式，更稳更省 token，但语义同构。

### 6.3 关键工程细节

| 关注点 | 做法 |
|---|---|
| **终止条件** | ① 模型给出 final answer；② 达到 `max_iterations`；③ 触发预算（token / 时长 / 费用）；④ 工具连续报错 N 次；⑤ 用户中断。 |
| **错误处理** | 工具异常**包成 Observation 回灌**，让模型自己决定重试 / 换路径，而不是直接抛出终止循环。 |
| **上下文管理** | 长循环必做：滚动摘要（Compaction）、工具结果截断、关键 Thought 钉住、向量化召回。 |
| **并行 tool_call** | 现代 LLM 支持一轮返回多个 tool_calls，宿主可并发执行后**一次性回填**，显著降延迟。 |
| **安全** | Tool 必须沙箱化（路径白名单、命令白名单、网络隔离）；写操作走**确认门**。 |
| **可观测** | 给每轮打 trace（thought / action / args / obs / latency / tokens），便于回放和评测。 |
| **反思插入** | 在第 N 轮后强制插入一个 "Self-Critique" Thought，可显著提升复杂任务成功率（Reflexion 思路）。 |
| **判停防呆** | 模型有时会"假装完成"，可加一个 verifier 工具或 LLM-as-Judge 二次确认。 |

### 6.4 一个最小 Python 骨架

```python
def agent_loop(user_query, tools, max_iter=25):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user",   "content": user_query}]
    for step in range(max_iter):
        resp = llm.chat(messages, tools=tools)
        messages.append(resp.message)
        if not resp.tool_calls:                     # 终止
            return resp.message.content
        for call in resp.tool_calls:                # 可改 asyncio.gather 并行
            try:
                result = TOOLS[call.name](**call.args)
            except Exception as e:
                result = f"ERROR: {e}"              # 错误回灌
            messages.append({"role": "tool",
                             "tool_call_id": call.id,
                             "content": str(result)[:8000]})  # 截断
    return "Reached max iterations."
```

## 7. How much（成本与规模）

| 维度 | 经验值 / 量级 |
|---|---|
| **轮次** | 简单任务 1~5 轮；编码 / 研究类 10~50 轮；复杂工程 100+ 轮（此时应考虑 Compaction 或 Sub-agent）。 |
| **Token 成本** | 上下文随轮次**近似线性增长**；总 token ≈ Σ(prompt_i)，prompt_i 含全部历史。一个 30 轮的编码任务通常消耗 50k~300k tokens。 |
| **延迟** | 端到端 ≈ Σ(LLM_latency + tool_latency)。串行下，每轮 2~10s，30 轮即 1~5 分钟。并行 tool_calls 可压缩 30%~60%。 |
| **可靠性** | 单体 ReAct 在 SWE-bench / GAIA 等基准上，通常比"无循环"提升 20~40 个百分点，但比多 Agent + Planner 仍有 5~15 点差距。 |
| **工程成本** | 极低：一个文件、一个循环即可起步；难点在 **Tool 设计**和**上下文工程**，而非循环本身。 |
| **运维成本** | 主要在 **Token 账单**和**沙箱安全**；需要可观测平台（Langfuse / Phoenix / OTel）兜底。 |

---

## 一句话总结

**Agent Loop 单体循环（ReAct）= 一个 while 循环里，让同一个 LLM 反复"想一步、做一步、看一步"，用最少的架构换取最强的灵活性与可解释性；它是当今绝大多数实用 Agent（尤其是编码 Agent）的事实基线，所有更复杂的多 Agent / 图式编排，都是在它"扛不住"时才被引入的扩展。**
