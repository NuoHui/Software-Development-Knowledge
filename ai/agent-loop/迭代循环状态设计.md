## `State` 原始定义

对应代码中的这段：

```ts
type State = {
  messages: Message[]
  toolUseContext: ToolUseContext
  autoCompactTracking: AutoCompactTrackingState | undefined
  maxOutputTokensRecoveryCount: number
  hasAttemptedReactiveCompact: boolean
  maxOutputTokensOverride: number | undefined
  pendingToolUseSummary: Promise<ToolUseSummaryMessage | null> | undefined
  stopHookActive: boolean | undefined
  turnCount: number
  transition: Continue | undefined
}
```

---

## 字段逐个说明

### [`messages: Message[]`](command:gongfeng.gongfeng-copilot.chat.open-symbol-in-file?%5B%7B%22%24mid%22%3A1%2C%22fsPath%22%3A%22%2FUsers%2Faedanxu%2FDownloads%2Fclaude-code-sourcemap-main%2Frestored-src%2Fsrc%2Fquery.ts%22%2C%22external%22%3A%22file%3A%2F%2F%2FUsers%2Faedanxu%2FDownloads%2Fclaude-code-sourcemap-main%2Frestored-src%2Fsrc%2Fquery.ts%22%2C%22path%22%3A%22%2FUsers%2Faedanxu%2FDownloads%2Fclaude-code-sourcemap-main%2Frestored-src%2Fsrc%2Fquery.ts%22%2C%22scheme%22%3A%22file%22%7D%2C%22messages%3A%20Message%5B%5D%22%2C%5B%7B%22line%22%3A312%2C%22character%22%3A6%7D%2C%7B%22line%22%3A312%2C%22character%22%3A14%7D%5D%5D)

#### 含义

这是**当前已经累计的消息历史**，也是下一轮构造 `messagesForQuery` 的基础输入。

它会随着主循环不断扩展，典型内容包括：

- 用户消息
- assistant 消息
- tool result
- attachment
- compact 后的边界消息 / summary 消息

#### 解决什么问题

它解决的是：

- **多轮 agent 推理需要保留完整上下文**
- 模型发起工具调用后，工具结果要回注到历史里，下一轮模型才能继续
- stop hook / compact / 预算控制都依赖完整消息链路

如果没有这个字段，`queryLoop` 每一轮都会“失忆”，无法形成真正的 agent 闭环。

#### 用于什么场景

主要场景：

- **正常多轮推进**
  - 把 `assistant` 输出和 `tool_result` 拼回去，进入下一轮
- **压缩恢复**
  - compact 后用压缩后的消息替换旧上下文
- **错误恢复**
  - `max_output_tokens` 恢复时，在原上下文后追加 meta 提示继续
- **stop hook 阻塞重试**
  - 把 hook 生成的 blocking error 注入到 `messages`

#### 一句话理解

`messages` 是整个 `queryLoop` 的**主上下文载体**。

---

### `toolUseContext: ToolUseContext`

#### 含义

这是**工具调用相关的运行上下文**，不只是工具定义本身，还包括很多与“当前 agent 执行环境”有关的信息。

从源码使用方式看，它承载了很多内容，例如：

- `options.tools`
- `abortController`
- `queryTracking`
- `agentId`
- `readFileState`
- `contentReplacementState`
- `getAppState()`
- `refreshTools()`
- 通知能力、附加 system message 能力等

#### 解决什么问题

它解决的是：

- **模型输出 `tool_use` 后，系统要知道怎么执行这些工具**
- 工具执行过程要共享一套环境
- 工具执行后可能会更新上下文
- 中断、权限、MCP、agent 身份都要贯穿整个 loop

如果只有 `messages`，是无法表达“这个 agent 当前能用哪些工具、以什么权限运行、是否被中断、是不是子 agent”的。

#### 用于什么场景

典型场景：

- **执行工具**
  - `runTools(...)`
  - `StreamingToolExecutor(...)`
- **中断控制**
  - `toolUseContext.abortController.signal.aborted`
- **获取应用状态**
  - 权限模式、fast mode、MCP 状态等
- **附加上下文**
  - memory / skill / attachment 相关能力
- **跨轮更新**
  - 工具执行返回 `newContext` 后会更新它

#### 一句话理解

`toolUseContext` 是**消息之外的执行环境容器**。

---

### `autoCompactTracking: AutoCompactTrackingState | undefined`

#### 含义

这是**自动压缩（autocompact）相关的追踪状态**。

它不是“是否压缩过”这么简单，而是记录：

- 当前是否已经 compact 过
- compact turn 的标识
- compact 后又继续了多少轮
- 连续失败次数等

#### 解决什么问题

自动压缩不是一个单点动作，而是一个**跨多轮的策略行为**。这个字段解决的是：

- compact 之后，后续几轮要知道自己处于什么 compact 状态
- 避免压缩失败后无限重试
- 记录 compact 后又继续了多少轮，便于埋点与阈值控制

如果没有这个状态，自动压缩会退化成“每轮重新判断”，很难做连续失败保护和 post-compact tracking。

#### 用于什么场景

- **autocompact 调用前后**
  - 传入旧 tracking
  - 返回后更新 tracking
- **compact 成功后**
  - 重置为新的 compact turn 状态
- **compact 失败后**
  - 记录 `consecutiveFailures`
- **tool 后下一轮**
  - `tracking.turnCounter++`

#### 一句话理解

`autoCompactTracking` 是**自动压缩子系统的跨轮状态记忆**。

---

### `maxOutputTokensRecoveryCount: number`

#### 含义

这是**针对 `max_output_tokens` 截断错误的恢复次数计数器**。

在代码里，`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`，所以它用来限制恢复尝试次数。

#### 解决什么问题

模型有时不是逻辑失败，而是**输出太长被截断**。这时系统会尝试恢复：

- 先提额重试
- 再插入 meta message，让模型“从中间接着做”

但如果不限制次数，就可能出现死循环：

- 截断
- 恢复
- 再截断
- 再恢复

这个字段就是为了解决这个问题。

#### 用于什么场景

- **遇到 `isWithheldMaxOutputTokens(lastMessage)`**
  - 判断是否还能恢复
- **恢复成功进入下一轮**
  - `maxOutputTokensRecoveryCount + 1`
- **正常进入新工具轮次**
  - 通常会重置为 `0`

#### 一句话理解

`maxOutputTokensRecoveryCount` 用来**限制“输出截断后的自动续跑次数”**。

---

### `hasAttemptedReactiveCompact: boolean`

#### 含义

表示**当前这条恢复链路里，是否已经尝试过 reactive compact**。

reactive compact 是一种“出了问题再压缩再重试”的补救策略，常用于：

- prompt too long
- 媒体过大
- 某些超限恢复场景

#### 解决什么问题

它解决的是**恢复逻辑死循环**。

比如：

1. 请求过长
2. reactive compact 一次
3. 继续请求
4. 还是过长
5. 如果不记录“已经尝试过”，就会无限重复 compact → retry

源码里的注释也明确提到，这个字段是为了避免：

- prompt-too-long + stop-hook blocking 这类链路中反复重试，烧掉大量 API 调用

#### 用于什么场景

- **prompt too long 恢复**
- **媒体大小错误恢复**
- **stop hook 阻塞后再次重试时**
  - 这个值会被保留，避免重复 compact

#### 一句话理解

`hasAttemptedReactiveCompact` 是**反应式压缩恢复的防重试保险丝**。

---

### `maxOutputTokensOverride: number | undefined`

#### 含义

表示**本轮模型调用是否临时覆盖默认的最大输出 token 数**。

典型场景是第一次遇到 `max_output_tokens` 时，把默认上限提升到：

- `ESCALATED_MAX_TOKENS`

#### 解决什么问题

有些截断并不需要复杂恢复，只是默认输出上限太小。

这个字段解决的问题是：

- **让同一轮请求可以临时切到更高输出额度**
- 而不是立刻进入多轮恢复对话

这样能减少：

- 不必要的恢复 message
- 模型重复解释
- 额外的轮次消耗

#### 用于什么场景

- **第一次命中 max output 限制**
  - 设置为 `ESCALATED_MAX_TOKENS`
- **下一次真正发请求时**
  - 传到 `callModel(...)`
- **继续到后续轮次**
  - 通常会清空恢复为 `undefined`

#### 一句话理解

`maxOutputTokensOverride` 是**一次性的输出上限临时提额开关**。

---

### `pendingToolUseSummary: Promise<ToolUseSummaryMessage | null> | undefined`

#### 含义

这是一个**异步中的工具使用摘要任务**。

不是摘要结果本身，而是一个尚未完成的 `Promise`。

源码里在工具执行完成后会异步触发：

- `generateToolUseSummary(...)`

然后把这个 promise 存入 `State`，到**下一轮开头**再尝试 `await` 并输出 summary。

#### 解决什么问题

工具摘要本身要额外调用模型或做异步生成，如果同步等它：

- 会阻塞当前主流程
- 增加用户等待时间

这个字段解决的是：

- **摘要生成异步化**
- **把耗时工作藏到下一轮开始前**
- **既保留可观测性，又不拖慢当前工具链路**

#### 用于什么场景

- **本轮有 tool use 执行完成后**
  - 创建 `nextPendingToolUseSummary`
- **下一轮开始时**
  - 如果存在，就 await 后 yield summary

#### 一句话理解

`pendingToolUseSummary` 是**“上轮工具摘要，延迟到下轮输出”的异步占位符**。

---

### `stopHookActive: boolean | undefined`

#### 含义

表示**当前是不是处在 stop hook 触发后的继续链路里**，或者说 stop hook 是否已进入活跃状态。

这个值会传给：

- `handleStopHooks(...)`

#### 解决什么问题

stop hook 不是简单“执行完就结束”，它可能：

- 产生 blocking errors
- 阻止 continuation
- 把 hook 结果转成 meta user message
- 触发再次进入主循环

所以系统需要知道当前是否处在 stop hook 驱动的后续处理中，避免逻辑混乱。

#### 用于什么场景

- **正常 assistant 完成后**
  - 执行 stop hooks
- **如果 hook 返回 blockingErrors**
  - 下一轮会把 `stopHookActive: true` 带上
- **后续重试时**
  - 让 hook 子系统知道当前是 stop-hook 继续链路

#### 一句话理解

`stopHookActive` 是**stop hook 相关重试/续跑链路的状态标记**。

---

### `turnCount: number`

#### 含义

这是**当前 `queryLoop` 已经推进到第几轮**。

初始化为 `1`，每次工具结果进入下一轮时递增。

#### 解决什么问题

`queryLoop` 虽然表面是一个函数，但实际上是一个**多轮递归式 agent turn**。所以必须知道当前已经跑了多少轮，用来：

- 防止无限循环
- 统计本轮内部执行深度
- 配合 attachment / task summary / maxTurns 控制

#### 用于什么场景

- **每次有 tool result 进入下一轮**
  - `nextTurnCount = turnCount + 1`
- **检查 `maxTurns`**
  - 如果超限，直接返回 `max_turns`
- **memory prefetch consume 记录**
  - `consumedOnIteration = turnCount - 1`

#### 一句话理解

`turnCount` 是**当前 agent 回合内部的轮次计数器**。

---

### `transition: Continue | undefined`

#### 含义

这是**上一轮为什么没有结束，而是继续进入这一轮**的原因记录。

源码注释写得很清楚：

```ts
// Why the previous iteration continued. Undefined on first iteration.
// Lets tests assert recovery paths fired without inspecting message contents.
```

也就是：

- 第一轮时它是 `undefined`
- 后续每次 `continue` 前会写入一个具体原因

例如代码里出现过的 reason 包括：

- `collapse_drain_retry`
- `reactive_compact_retry`
- `max_output_tokens_escalate`
- `max_output_tokens_recovery`
- `stop_hook_blocking`
- `token_budget_continuation`
- `next_turn`

#### 解决什么问题

它解决的是**主循环“为什么继续”的可观测性问题**。

如果没有这个字段，测试或调试只能通过：

- 看消息内容
- 猜是哪个恢复路径触发了继续

这会非常脆弱。

有了它之后：

- 测试可以断言某个恢复路径确实发生
- 调试时更容易看懂当前是“正常下一轮”还是“错误恢复重试”

#### 用于什么场景

- **prompt too long 后 collapse drain 重试**
- **reactive compact 重试**
- **max output 提额重试**
- **max output 恢复 message 重试**
- **stop hook blocking 后继续**
- **token budget nudging 后继续**
- **正常 tool result 驱动的下一轮**

#### 一句话理解

`transition` 是**主循环继续原因的显式状态记录**。

## 从设计角度看，为什么 `State` 这些字段值得放在一起

这些字段并不是随便堆在一起的，它们有明显的分层：

### 1. 上下文主数据
- `messages`
- `toolUseContext`

这两个决定“下一轮请求拿什么去跑”。

---

### 2. 恢复控制状态
- `maxOutputTokensRecoveryCount`
- `hasAttemptedReactiveCompact`
- `maxOutputTokensOverride`

这三个都是**恢复链路保护字段**，目的都是防止错误恢复失控。

---

### 3. 压缩与性能状态
- `autoCompactTracking`
- `pendingToolUseSummary`

一个管上下文压缩，一个管异步摘要，都是为了让长对话还能稳定跑。

---

### 4. 流程控制状态
- `stopHookActive`
- `turnCount`
- `transition`

这三个负责“主循环现在处于哪种继续路径”。

---

## 你可以把 `State` 简单记成这四类

### **上下文**
- `messages`
- `toolUseContext`

### **压缩 / 性能**
- `autoCompactTracking`
- `pendingToolUseSummary`

### **恢复保护**
- `maxOutputTokensRecoveryCount`
- `hasAttemptedReactiveCompact`
- `maxOutputTokensOverride`

### **流程控制**
- `stopHookActive`
- `turnCount`
- `transition`

---

## 最后给一个最简理解版

如果只用一句话概括每个字段：

- `messages`：**下一轮推理要带上的消息历史**
- `toolUseContext`：**工具执行环境和运行控制上下文**
- `autoCompactTracking`：**自动压缩状态追踪**
- `maxOutputTokensRecoveryCount`：**输出截断恢复次数**
- `hasAttemptedReactiveCompact`：**是否已经做过 reactive compact，防止死循环**
- `maxOutputTokensOverride`：**当前轮临时提高输出 token 上限**
- `pendingToolUseSummary`：**上一轮工具摘要的异步结果占位**
- `stopHookActive`：**是否处在 stop hook 引发的继续链路中**
- `turnCount`：**当前 query 内部已经跑到第几轮**
- `transition`：**上一轮为什么继续到这一轮**
