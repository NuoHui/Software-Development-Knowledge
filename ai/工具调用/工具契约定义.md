

### 对照表

下面我按 `Tool.ts` 里的定义，把 `Tool` 契约整理成“**字段 -> 责任 -> 调用时机 -> 典型实现**”的表。  
为了可读性，我按层次拆成几组；最后再用 `TaskGetTool.ts` 和 `ToolSearchTool.ts` 做一个落地映射。

---

### 1）身份与发现

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `name` | 工具主标识，模型发起调用、系统查找工具都靠它 | 工具注册、模型输出 `tool_use`、运行时查找 | `TaskGet`、`ToolSearch` 这类唯一名称 |
| `aliases?` | 兼容旧工具名，避免重命名后历史 prompt / transcript 失效 | `findToolByName()`、历史兼容、迁移期 | 旧名保留为别名 |
| `searchHint?` | 给 ToolSearch 的关键词召回补充语义 | deferred tool 被搜索时参与匹配和打分 | `TaskGetTool.ts` 里的 `retrieve a task by ID` |
| `mcpInfo?` | 保存 MCP server/tool 的原始身份 | MCP 工具装配、桥接外部 server 时 | `{ serverName, toolName }` |

---

### 2）模型协议：模型怎么理解并调用这个工具

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `inputSchema` | 定义输入参数结构，是最核心的调用契约 | 工具注册给模型、参数校验、调用前解析 | `z.object({ taskId: z.string() })` |
| `inputJSONSchema?` | 给不能直接用 Zod 表达的场景，尤其 MCP | 装配工具 schema 时 | 直接提供 JSON Schema |
| `outputSchema?` | 约束工具输出结构，便于消费方理解结果 | 工具定义、输出规范化、测试校验 | `z.object({ task: ... })` |
| `description(input, options)` | 返回“这次调用视角下”的工具说明 | 构建工具描述、需要动态说明时 | 根据会话模式返回不同文案 |
| `prompt(options)` | 返回提供给模型的工具说明文本，通常是主描述 | 首轮工具注入、ToolSearch 对描述建索引时 | `ToolSearchTool.ts` 中直接复用 `getPrompt()` |
| `strict?` | 开启更严格的 schema / 指令遵守模式 | API 组装工具定义时 | 高约束工具可开启 |

---

### 3）执行：工具真正做什么

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `call(args, context, canUseTool, parentMessage, onProgress)` | 真正执行业务逻辑，返回 `ToolResult` | 模型触发工具调用后 | 查任务、搜工具、读文件、执行命令 |
| `inputsEquivalent?(a, b)` | 判断两个输入是否等价，便于去重或优化 | 调度、重试、复用判断时 | 比较路径/命令/参数是否语义一致 |
| `backfillObservableInput?(input)` | 给观察者看到的输入补充兼容字段，不改原始 API 输入 | transcript / SDK stream / hook / permission 观察前 | 补 legacy 字段、派生字段 |

---

### 4）安全与权限

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `validateInput?(input, context)` | 业务语义校验；告诉模型“这个输入不合法” | **在权限检查之前** | 检查路径是否为空、参数组合是否冲突 |
| `checkPermissions(input, context)` | 做工具级权限判断；决定 allow / deny / ask | `validateInput()` 通过后 | 写文件工具 ask，读文件工具 allow |
| `isReadOnly(input)` | 声明是不是只读操作 | 权限策略、UI 展示、安全模式判断 | 查询类工具返回 `true` |
| `isDestructive?(input)` | 声明是不是破坏性不可逆操作 | 权限策略、风险提示 | 删除、覆盖、发送消息返回 `true` |
| `requiresUserInteraction?()` | 表示执行依赖用户交互 | 调度与交互策略判断 | 提问型工具、确认型工具 |
| `isOpenWorld?(input)` | 标识是否会访问外部世界/网络 | 安全分类、提示策略 | 网页抓取、WebSearch 返回 `true` |
| `preparePermissionMatcher?(input)` | 为 hook / 权限规则做模式匹配预处理 | 权限规则匹配前 | 把 `Bash(git *)` 这种规则转成 matcher |
| `getPath?(input)` | 提供与当前工具关联的路径，便于权限/展示/规则处理 | 路径型工具的辅助流程中 | 读文件、编辑文件返回目标路径 |

---

### 5）调度与生命周期

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `isEnabled()` | 当前环境下工具是否可用 | 构建可用工具列表时 | feature flag、环境能力、配置开关 |
| `isConcurrencySafe(input)` | 是否可并发执行 | 调度器安排并行调用时 | 搜索/只读查询常为 `true` |
| `interruptBehavior?()` | 用户中断时，工具应取消还是阻塞后续消息 | 工具运行中收到新用户消息时 | 长跑工具 `cancel`，关键任务 `block` |
| `isMcp?` | 标记 MCP 工具 | MCP 相关调度、UI、透传逻辑 | 外部 server 工具 |
| `isLsp?` | 标记 LSP 工具 | LSP 相关调度与分类 | 符号/诊断类工具 |
| `shouldDefer?` | 允许工具被延迟加载，不在首轮完整展开 schema | ToolSearch 模式下构建首轮工具列表时 | `TaskGetTool.ts` 的 `shouldDefer: true` |
| `alwaysLoad?` | 即使启用 ToolSearch，也强制首轮完整加载 | 与 `shouldDefer` 对冲，在工具集装配时生效 | turn 1 必须暴露给模型的工具 |

---

### 6）结果预算与持久化

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `maxResultSizeChars` | 控制工具结果过大时是否落盘、只给预览 | 工具产出结果后，写回模型前 | 普通工具 `100_000`；绝不能持久化可设 `Infinity` |

---

### 7）给自动分类器/系统观察者用的字段

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `toAutoClassifierInput(input)` | 给自动安全分类器提供紧凑输入摘要 | 自动安全分类、风险判断前 | Bash 返回命令串；低风险工具返回空串 |
| `isSearchOrReadCommand?(input)` | 告诉 UI 这是不是“搜索/读取/列目录”类操作 | UI 折叠显示、摘要展示时 | grep/read/ls 类工具返回结构体 |

---

### 8）结果如何回给模型

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `mapToolResultToToolResultBlockParam(content, toolUseID)` | 把内部 `Output` 转成真正发回模型的 `tool_result` 协议块 | `call()` 返回后、写入 transcript / API 前 | 文本结果、结构化块、`tool_reference` 列表 |

这个字段**非常关键**，因为它决定：

- 内部业务输出长什么样
- 模型最终看到的结果长什么样

这两者可以完全不同。

---

### 9）UI 展示：给用户看什么

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `userFacingName(input)` | 给 UI 显示的人类可读名称 | transcript / 工具气泡展示时 | 默认回落为 `name` |
| `userFacingNameBackgroundColor?()` | 给 UI 名称打标签色 | UI 渲染时 | 不同工具类别不同颜色 |
| `renderToolUseMessage(input, options)` | 渲染“工具开始执行”的消息 | 工具参数还在流式输入或刚开始执行时 | “Reading file…”、“Searching…” |
| `renderToolResultMessage?(content, progress, options)` | 渲染结果 UI | 工具完成后 | 表格、diff、结果卡片 |
| `renderToolUseProgressMessage?(progress, options)` | 渲染中间进度 UI | 工具运行过程中有 progress 时 | 进度条、流式状态 |
| `renderToolUseQueuedMessage?()` | 渲染排队状态 | 工具尚未开始执行但已排队时 | “Queued…” |
| `renderToolUseRejectedMessage?(...)` | 被拒绝时给自定义 UI | 权限拒绝后 | 编辑类工具展示 rejected diff |
| `renderToolUseErrorMessage?(...)` | 错误时给自定义 UI | 执行报错后 | “File not found” 这类友好错误 |
| `renderGroupedToolUse?(toolUses, options)` | 多个并行工具合并展示 | 非 verbose 模式、并行工具同组时 | 多个搜索结果折叠成一组 |
| `renderToolUseTag?(input)` | 给工具消息追加元信息标签 | UI 展示时 | timeout、resume ID、model 名称 |
| `getToolUseSummary?(input)` | 为紧凑模式提供一句摘要 | condensed view | “Read 3 files” |
| `getActivityDescription?(input)` | spinner 里的进行时描述 | 执行中 spinner | “Reading src/foo.ts” |
| `isResultTruncated?(output)` | 告诉 UI 当前非 verbose 是否被截断 | 渲染折叠态时 | 大结果可点击展开 |

---

### 10）给 transcript 搜索/索引用的字段

| 字段 | 责任 | 调用时机 | 典型实现 |
| --- | --- | --- | --- |
| `extractSearchText?(out)` | 提供 transcript 搜索索引文本，应尽量和实际渲染一致 | 索引构建、搜索高亮时 | 从结果中提取可搜索文本 |

这个字段的重点不是“模型看什么”，而是“**用户在 transcript 里搜什么**”。

---

### 11）`buildTool()` 默认补齐的字段

`Tool.ts` 里 `buildTool()` 会为一些常见字段提供默认值，所以很多工具文件里看起来只实现了一部分契约。

| 字段 | 默认值 | 默认语义 |
| --- | --- | --- |
| `isEnabled` | `true` | 默认启用 |
| `isConcurrencySafe` | `false` | 默认认为**不适合并发** |
| `isReadOnly` | `false` | 默认认为**可能写入/有副作用** |
| `isDestructive` | `false` | 默认非破坏性 |
| `checkPermissions` | `allow` | 默认交给通用权限系统 |
| `toAutoClassifierInput` | `''` | 默认不参与自动安全分类 |
| `userFacingName` | `name` | 默认 UI 名称等于工具名 |

这里的设计思路很清楚：  
**能 fail-closed 的地方尽量 fail-closed。**

比如：

- `isConcurrencySafe` 默认 `false`
- `isReadOnly` 默认 `false`

这都属于偏保守的系统设计。

### 用一个工具把整张表串起来：`TaskGetTool`

看 `TaskGetTool.ts`，它几乎是一个很标准的“查询类 deferred tool”样板：

| 字段 | 在这个工具里的实现 | 说明 |
| --- | --- | --- |
| `name` | `TASK_GET_TOOL_NAME` | 内部协议主键 |
| `searchHint` | `retrieve a task by ID` | 方便被 ToolSearch 命中 |
| `inputSchema` | `taskId: string` | 模型只能按 ID 查询 |
| `outputSchema` | `{ task: ... | null }` | 返回结构稳定 |
| `description` / `prompt` | 固定文案 | 让模型知道用途 |
| `call` | `getTask(taskListId, taskId)` | 真正查询任务 |
| `shouldDefer` | `true` | 默认不首轮全量暴露 |
| `isEnabled` | `isTodoV2Enabled()` | 受功能开关控制 |
| `isConcurrencySafe` | `true` | 读操作可并发 |
| `isReadOnly` | `true` | 只读 |
| `toAutoClassifierInput` | `taskId` | 给分类器一个紧凑输入 |
| `renderToolUseMessage` | `null` | 不额外展示调用气泡 |
| `mapToolResultToToolResultBlockParam` | 把 task 格式化成文本 | 内部结构化数据转模型可读文本 |

所以如果把它一句话概括，就是：

**“一个受 feature flag 控制的、只读可并发的 deferred 查询工具，模型先通过 ToolSearch 找到它，再按 `taskId` 调用，最后把结构化结果转成文本 `tool_result`。”**

### 再补一个协议型工具：`ToolSearchTool`

`ToolSearchTool.ts` 则体现了“系统工具”的契约特点：

| 字段 | 在这个工具里的实现 | 说明 |
| --- | --- | --- |
| `isEnabled` | `isToolSearchEnabledOptimistic()` | 只有启用 ToolSearch 机制时才可用 |
| `isReadOnly` | `true` | 纯查询 |
| `isConcurrencySafe` | `true` | 搜索可并发 |
| `inputSchema` | `query`、`max_results` | 允许 `select:xxx` 或关键词搜索 |
| `call` | 从 `tools` 中筛 deferred tools，做匹配与排序 | 系统级调度工具 |
| `mapToolResultToToolResultBlockParam` | 返回 `tool_reference` blocks | 结果不是普通文本，而是“工具引用” |
| `renderToolUseMessage` | `null` | UI 不强调它自身 |
| `userFacingName` | 空字符串 | 更像协议桥，而不是用户显式操作的业务工具 |

这也说明：

**同一套 `Tool` 契约既能描述“业务动作”，也能描述“工具装载协议动作”。**
