# 模块化

## 进化历史


```
全局 script
↓
AMD (RequireJS)
↓
CommonJS (Node)
↓
ES Module (ESM)
```
目前主流：

浏览器 / 工程化：ES Module
Node：CommonJS + ESM


| 特性           | CommonJS       | ESM          |
| ------------ | -------------- | ------------ |
| 加载时机         | 运行时            | 编译时          |
| 导入方式         | require        | import       |
| 导出           | module.exports | export       |
| 值类型          | 值拷贝            | live binding(引用绑定) |
| 是否同步         | 同步             | 异步           |
| tree shaking | 不支持            | 支持           |


CJS 支持运行时加载、运行时解析。
```javascript
if (condition) {
  require('./a')
}
```

## 经典题


### CommonJS 与 ESM 最大区别是什么？

CommonJS 是运行时加载。
ESM 是编译时加载。

ESM 构建静态依赖图
支持 tree-shaking。

### ESM 引用绑定


```javascript
// a.js
export let count = 0

setTimeout(() => {
  count++
}, 1000)
```

```javascript
// b.js
import { count } from './a'

setTimeout(() => {
  console.log(count) // 1， ESM 是 live binding，不是值拷贝。
}, 2000)
```

### CJS 值拷贝


```javascript
// CommonJS
exports.count = 0

setTimeout(() => {
  exports.count++
}, 1000)
```
```javascript
const { count } = require('./a')

setTimeout(() => {
  console.log(count) // 0 解构时发生值拷贝
}, 2000)
```
### 循环依赖

```javascript
// a.js
exports.done = false
const b = require('./b')
console.log(b.done)
exports.done = true
```

```javascript
// b.js
exports.done = false
const a = require('./a')
console.log(a.done)
exports.done = true
```

输出：
```
false
false
```
Why：
```
CommonJS 返回：

未执行完成的 exports
```

### 为什么 ESM 需要写在顶层？

ESM 是“静态模块系统”,ESM 在 编译阶段就要构建模块依赖图（Module Dependency Graph）。

```
解析代码
↓
收集所有 import/export
↓
构建模块依赖图
↓
初始化模块
↓
执行代码
```

如果你的import 写在任意位置，甚至if判断里面，那么依赖关系就不是固定的，编译阶段无法确定依赖。

静态依赖图的作用：

```
tree-shaking
code splitting
scope hoisting
dead code elimination
```


### 为什么 Tree Shaking 依赖 ESM

tree shaking 是删除未被使用的代码。
因此它需要做依赖分析，确认哪些代码是没有被引用到的。

因此在 编译阶段就能确定。

#### 为什么 export default 会影响 tree-shaking，而 named export 更好？

```javascript
// utils.js
export function foo() {}
export function bar() {}
export function baz() {}
```
使用方


```javascript
import { foo } from './utils'
```

打包器可以生成对应依赖图：

```javascript
utils
 ├── foo (used)
 ├── bar (unused)
 └── baz (unused)
```
因为 named export 是静态结构。导出名称是明确的。

如果是 export default

```javascript
// utils.js
export default {
  foo() {},
  bar() {},
  baz() {}
}
```

```javascript
import utils from './utils'

utils.foo()
```

打包器是无法知道，bar / baz 是否被使用。

```javascript
utils[methodName]() // 这种运行时动态写法，打包器怎么知道谁被引用了，只能保留整个对象
```
