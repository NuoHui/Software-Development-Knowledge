# V8 Deoptimization 深度解析：为什么优化代码会退回去？

一句话解释：

> **V8 的优化代码之所以会退回去，是因为优化代码不是“通用 JS 语义代码”，而是基于历史运行反馈生成的“带假设的高速机器码”。一旦运行时行为打破这些假设，V8 必须 deopt，退回到更通用、更安全的执行路径，保证 JS 语义正确。**

V8 官方也明确把它称为 **speculative optimization**：JIT 编译器根据早期执行收集到的 feedback 做假设，比如 `a + b` 过去一直是整数相加，就生成整数加法机器码；如果后面参数变成字符串、浮点数或对象，假设被破坏，V8 就会执行 deoptimization，丢弃优化代码，回到未优化代码并继续收集反馈。([V8][1])

---

# 1. 什么是 Deoptimization？

**Deoptimization，简称 deopt，本质是：**

> 从优化后的机器码，退回到解释器 / baseline 执行状态。

现代 V8 执行 JS 大致是多层架构：

```txt
JS 源码
  ↓
Ignition Bytecode
  ↓
解释执行，收集反馈 FeedbackVector / IC
  ↓
Sparkplug / Maglev / TurboFan 优化编译
  ↓
优化机器码执行
  ↓
假设失效
  ↓
Deoptimization
  ↓
回到 Ignition / baseline 状态继续执行
```

V8 的 Ignition bytecode 不只是解释器输入，它也是优化编译和 deopt 回退的重要基准状态。V8 官方提到，Ignition bytecode 可以直接用于 TurboFan 生成优化代码，同时也让 deoptimization 机制更简洁、更可靠。([V8][2])

所以你可以把 V8 的优化理解为：

```txt
不是：JS 代码 → 永久优化机器码

而是：JS 代码 → 根据当前行为生成快路径机器码
      如果行为变了 → 回到安全路径
      如果新行为稳定 → 可能再次优化
```

# 2. 为什么 V8 必须做 Deoptimization？

因为 JavaScript 太动态。

比如这段代码：

```js
function add(a, b) {
  return a + b;
}

for (let i = 0; i < 100000; i++) {
  add(i, i + 1);
}

add("hello", "world");
```

前面 10 万次，V8 看到的是：

```txt
a: Smi 小整数
b: Smi 小整数
操作: 数字加法
返回值: 数字
```

于是 TurboFan / Maglev 可能生成类似这样的优化逻辑：

```txt
检查 a 是 Smi
检查 b 是 Smi
执行机器级整数加法
如果溢出或类型不对，deopt
```

优化后，它不需要完整执行 JS 的 `+` 语义。

因为完整的 JS `+` 很复杂：

```txt
number + number
string + string
number + string
object + object
object.valueOf()
object.toString()
Symbol.toPrimitive
BigInt
异常路径
```

如果每次都走完整语义，性能会很差。于是 V8 选择“赌一把”：

```txt
过去都是整数 → 未来大概率还是整数 → 生成整数快路径
```

但最后一次：

```js
add("hello", "world");
```

参数变成字符串，优化假设失效。此时优化机器码不能继续执行，否则会把字符串当整数算，结果错误。

所以 V8 必须 deopt。

# 3. Deoptimization 的核心：优化代码依赖“假设”

V8 优化代码常见依赖这些假设：

```txt
1. 参数类型稳定
2. 返回值类型稳定
3. 对象 HiddenClass / Map 稳定
4. 属性偏移稳定
5. 数组 ElementsKind 稳定
6. 函数调用目标稳定
7. 原型链稳定
8. 全局变量 / 闭包变量类型稳定
9. 某些字段是 const / 不变值
10. 算术不会溢出
```

一旦这些假设被打破，优化代码就可能不再正确。

V8 对对象属性访问的优化高度依赖 HiddenClass / Map。V8 官方文档提到，对象属性在底层有不同表示方式，HiddenClasses 用来快速识别对象 shape，这是 inline cache 等优化的基础。([V8][3])

---

# 4. 例子一：类型假设失效

```js
function calc(x) {
  return x + 1;
}

for (let i = 0; i < 100000; i++) {
  calc(i);
}

calc("1");
```

前面 V8 看到：

```txt
x 是 Smi
x + 1 是整数加法
```

优化后可能是：

```txt
if (!isSmi(x)) deopt
return intAdd(x, 1)
```

当传入 `"1"`：

```txt
x 不是 Smi
触发 guard fail
进入 deoptimizer
重建解释器 frame
从 bytecode 位置继续执行完整 JS 语义
```

所以结果不是数字加法，而是：

```js
"1" + 1 // "11"
```

如果不 deopt，V8 就会算错。

---

# 5. 例子二：HiddenClass / Map 变化导致 deopt

```js
function getX(obj) {
  return obj.x;
}

const a = { x: 1, y: 2 };
const b = { x: 3, y: 4 };

for (let i = 0; i < 100000; i++) {
  getX(i % 2 ? a : b);
}

const c = { y: 1, x: 2 };
getX(c);
```

`a` 和 `b` 的属性添加顺序一致：

```js
{ x, y }
```

所以它们大概率有相同 HiddenClass：

```txt
MapA:
  x offset 0
  y offset 1
```

V8 优化 `getX` 时可以生成：

```txt
检查 obj.map === MapA
直接读取 offset 0
```

但是 `c` 是：

```js
{ y: 1, x: 2 }
```

它的属性顺序不同，HiddenClass 可能变成：

```txt
MapB:
  y offset 0
  x offset 1
```

这时优化代码里的：

```txt
读取 offset 0
```

会读到 `y`，不是 `x`。

所以必须 deopt。

---

# 6. 例子三：字段 const 假设失效

V8 有时会认为某个字段稳定不变，甚至直接把值常量折叠进优化代码。

例如官方 HiddenClass 文档里有一个例子：TurboFan 发现 `m2.cost` 是稳定值，于是优化后的 `foo()` 甚至直接返回那个字符串常量，而不是每次真的去对象里读属性。后来如果执行：

```js
m2.cost = "priceless";
```

V8 就必须让依赖这个字段常量的优化代码失效，否则函数会继续返回旧值。官方示例里 `--trace-deopt` 会看到 `reason: field-const`，表示因为字段常量假设被破坏而触发 deopt。([V8][4])

这类 deopt 非常关键：

```txt
优化前：
  return m2.cost

优化后：
  return "one arm, one leg"

字段被改：
  m2.cost = "priceless"

如果不 deopt：
  继续返回旧值，语义错误
```

所以 deopt 是正确性保障。

# 7. 例子四：数组 ElementsKind 变化

V8 对数组也有很多内部表示：

```txt
PACKED_SMI_ELEMENTS       // 紧凑小整数数组
PACKED_DOUBLE_ELEMENTS    // 紧凑浮点数数组
PACKED_ELEMENTS           // 普通对象数组
HOLEY_SMI_ELEMENTS        // 有洞小整数数组
HOLEY_DOUBLE_ELEMENTS     // 有洞浮点数组
HOLEY_ELEMENTS            // 有洞普通对象数组
DICTIONARY_ELEMENTS       // 稀疏数组 / 字典模式
```

比如：

```js
const arr = [1, 2, 3];
```

一开始可能是：

```txt
PACKED_SMI_ELEMENTS
```

然后：

```js
arr.push(4.5);
```

可能变成：

```txt
PACKED_DOUBLE_ELEMENTS
```

再然后：

```js
arr.push({});
```

可能变成：

```txt
PACKED_ELEMENTS
```

再比如：

```js
arr[100000] = 1;
```

可能转向更稀疏的表示。

优化代码如果之前假设：

```txt
这是连续 Smi 数组
可以直接按机器整数读取
不用处理 hole
不用处理对象
不用处理稀疏字典
```

那么一旦数组元素类型或结构变化，优化代码就不安全了。

典型触发场景：

```js
function sum(arr) {
  let s = 0;
  for (let i = 0; i < arr.length; i++) {
    s += arr[i];
  }
  return s;
}

const arr = [1, 2, 3, 4, 5];

for (let i = 0; i < 100000; i++) {
  sum(arr);
}

arr[2] = undefined;
sum(arr);
```

前面 V8 可能基于“纯数字紧凑数组”优化，后面混入 `undefined`，就可能破坏数值加法和 ElementsKind 假设。

# 8. 例子五：函数调用目标变化

```js
function run(fn, x) {
  return fn(x);
}

function double(x) {
  return x * 2;
}

for (let i = 0; i < 100000; i++) {
  run(double, i);
}

run(x => x + 1, 10);
run(x => String(x), 10);
run(Math.sqrt, 10);
```

前面 V8 看到：

```txt
run 的 fn 总是 double
```

于是可能会把调用内联：

```js
run(double, x)
```

优化成类似：

```js
return x * 2;
```

但是后面传入不同函数，原来的内联假设失效。

调用点从：

```txt
monomorphic 单态
```

变成：

```txt
polymorphic 多态
```

甚至：

```txt
megamorphic 超多态
```

这时原来的优化价值下降，甚至不再正确，于是需要 deopt 或重新优化成更通用的代码。

# 9. 例子六：Smi 整数溢出

V8 会优先把小整数存成 Smi，因为这样更省内存、操作也更快。V8 的 Maglev 文章提到，V8 会尝试把数字编码为 Small Integers，也就是 Smi，用于节省内存并提升整数操作性能。([V8][5])

例如：

```js
function inc(x) {
  return x + 1;
}

for (let i = 0; i < 100000; i++) {
  inc(i);
}

inc(2147483647);
```

如果优化代码假设：

```txt
x 是 31-bit Smi
x + 1 仍然是 Smi
```

那么当结果溢出 Smi 范围时，就不能继续用整数快路径。

因为 JS number 语义是 double，不是固定 32 位整数。V8 必须 deopt，退回到能正确处理 double / HeapNumber 的路径。

# 10. Deoptimization 内部到底发生了什么？

可以把 deopt 拆成 6 步：

```txt
1. 优化代码执行中遇到 guard
2. guard 检查失败
3. 跳转到 deoptimizer
4. 根据 deopt metadata / FrameState 重建解释器栈帧
5. 把寄存器、栈、常量中的值 materialize 回 JS 状态
6. 回到对应 bytecode offset 继续执行
```

关键点是：优化代码执行时，很多 JS 层面的东西已经不再真实存在了。

比如：

```js
function f(a, b) {
  const x = a + b;
  const y = x * 2;
  return y;
}
```

优化后：

```txt
a 可能在寄存器 rax
b 可能在寄存器 rbx
x 可能根本没有 materialize，只是 SSA 中间值
y 可能也只是机器寄存器里的值
```

如果此时发生 deopt，V8 必须把这些状态重新还原成解释器能理解的状态：

```txt
bytecode offset 是哪里？
局部变量 a 是什么？
局部变量 b 是什么？
局部变量 x 是什么？
临时寄存器状态是什么？
调用栈怎么恢复？
```

V8 官方在 Maglev 文章里提到，Maglev 会给可能 deopt 的节点附带 abstract interpreter frame state，这个状态会在代码生成阶段变成 metadata，用于把优化状态映射回未优化状态；deoptimizer 会读取解释器 frame 和机器寄存器里的值，然后放回解释器需要的位置。([V8][5])

这就是为什么优化编译器不能随便优化。它必须在关键位置保留：

```txt
deopt point
frame state
value mapping
resume point
materialization metadata
```

否则退不回来。

# 11. Eager Deopt 和 Lazy Deopt

Deoptimization 大体可以理解为两类。

## 11.1 Eager Deopt：执行到这里，立刻退

典型场景：

```txt
类型检查失败
Map 检查失败
Smi 检查失败
数组 bounds / elements 检查失败
整数溢出
```

例如：

```txt
if (!isSmi(x)) deopt
```

执行到这个 guard，发现 `x` 不是 Smi，立刻退。

---

## 11.2 Lazy Deopt：先标记失效，下次进入再退

有些 deopt 不是当前执行流里的 guard 失败，而是某个依赖被外部破坏。

例如：

```js
m2.cost = "priceless";
```

这会让依赖 `m2.cost` 常量的优化代码失效。

V8 可以把相关 optimized code 标记为：

```txt
marked_for_deoptimization
```

然后在下次进入这个优化函数时检查这个标记，再 unlink 优化代码，回到解释器入口。V8 的 lazy unlinking 文章提到，优化函数会链接到 optimized code；deopt 后需要 unlink 这个 code，避免再次执行无效代码。新的 lazy unlinking 做法是推迟到函数下次被调用时再 unlink。([V8][6])

简化理解：

```txt
Eager deopt:
  我正在跑，发现假设错了，马上退。

Lazy deopt:
  某个依赖被改了，我先把相关优化代码标记失效。
  下次你再调用它时，不让你继续跑旧优化代码。
```

# 12. Deoptimization 为什么会造成性能抖动？

因为 deopt 的成本不只是“慢一点”。

它通常包含：

```txt
1. 当前优化代码中断
2. 跳转到 runtime / deoptimizer
3. 重建解释器 frame
4. materialize 优化掉的对象 / 中间值
5. 回到解释器 / baseline
6. 之前优化代码可能被丢弃
7. 后续需要重新收集 feedback
8. 可能再次触发优化编译
```

所以频繁 deopt 会导致：

```txt
性能尖刺
主线程卡顿
JIT 编译开销上升
CPU 抖动
GC 压力变大
优化-退化-再优化循环
```

V8 甚至专门提到过一种 **deoptimization loop**：优化代码 deopt 之后，TurboFan 又尝试优化，但没有办法学到稳定规律，于是可能反复优化、反复退化，最后才放弃。V8 曾针对这类场景增加机制，比如数组高阶函数 callback 中改变数组 shape / length 时，后续不再内联该调用点。([V8][7])

# 13. 最常见的 deopt 触发场景

## 13.1 参数类型不稳定

不好：

```js
function normalize(v) {
  return v + 1;
}

normalize(1);
normalize(2);
normalize("3");
normalize({});
```

好：

```js
function normalizeNumber(v) {
  return Number(v) + 1;
}
```

或者在边界提前归一化：

```js
const n = typeof input === "number" ? input : Number(input);
```

---

## 13.2 对象 shape 不稳定

不好：

```js
const a = {};
a.x = 1;
a.y = 2;

const b = {};
b.y = 2;
b.x = 1;
```

好：

```js
function createPoint(x, y) {
  return {
    x,
    y,
  };
}
```

保持属性初始化顺序一致。

---

## 13.3 动态增删属性

不好：

```js
function update(cell) {
  cell.value = 1;

  if (someCondition) {
    cell.extra = {};
  }

  delete cell.value;
}
```

好：

```js
function createCell() {
  return {
    value: null,
    extra: null,
    status: 0,
  };
}
```

不要热路径里频繁 `delete`，可以用 `null` / `undefined` 标记状态。

---

## 13.4 数组元素类型混杂

不好：

```js
const rows = [1, 2, 3];
rows.push("4");
rows.push({});
```

好：

```js
const numericRows = [1, 2, 3];
const objectRows = [{ value: 1 }, { value: 2 }];
```

热路径数组尽量保持元素类型稳定。

---

## 13.5 创建 holey array

不好：

```js
const arr = [];
arr[10000] = 1;
```

不好：

```js
const arr = new Array(10000);
arr[9999] = 1;
```

更好：

```js
const arr = [];
for (let i = 0; i < 10000; i++) {
  arr.push(0);
}
```

或者明确使用 TypedArray：

```js
const arr = new Float64Array(10000);
```

---

## 13.6 热函数调用目标不稳定

不好：

```js
function apply(fn, value) {
  return fn(value);
}

apply(fn1, x);
apply(fn2, x);
apply(fn3, x);
apply(fn4, x);
```

好：

```js
function applyDouble(value) {
  return value * 2;
}

function applyFormat(value) {
  return String(value);
}
```

热路径里减少“万能函数 + 任意 callback”。

---

## 13.7 原型链变化

不好：

```js
function getName(obj) {
  return obj.name;
}

Object.setPrototypeOf(obj, newProto);
```

`Object.setPrototypeOf`、动态改 prototype、热路径 monkey patch 内建方法，都容易破坏 V8 对原型链和内联缓存的假设。

---

# 14. 从表格性能负责人视角看 Deoptimization

你负责的是表格业务，deopt 特别容易出现在这些模块。

## 14.1 单元格数据模型

不好：

```js
const cell = {
  value: 123,
};

if (hasFormula) {
  cell.formula = "=SUM(A1:A10)";
}

if (hasStyle) {
  cell.style = {};
}

if (hasComment) {
  cell.comment = {};
}
```

这会导致大量 cell 对象 shape 不一致。

更好的方式：

```js
function createCell() {
  return {
    value: null,
    formula: null,
    style: null,
    comment: null,
    validation: null,
    format: null,
    flags: 0,
  };
}
```

这样热路径访问：

```js
cell.value
cell.formula
cell.flags
```

会更加稳定。

---

## 14.2 渲染层 row / column / cell 对象

表格滚动、选区、公式高亮、条件格式、冻结窗格，都会高频访问对象属性。

建议：

```txt
1. 对象字段提前声明
2. 字段顺序稳定
3. 不在滚动热路径动态加属性
4. 不在高频路径 delete 属性
5. 区分 CellModel / CellViewModel / RenderCell
6. 避免一个对象承载所有平台、所有插件字段
```

---

## 14.3 公式计算结果类型

公式结果可能是：

```txt
number
string
boolean
error
array
blank
rich text
```

如果一个热函数直接处理所有类型：

```js
function normalizeResult(result) {
  if (result == null) return "";
  return result + "";
}
```

长期看容易让类型反馈变复杂。

更好的方式是先做 tagged union：

```ts
type FormulaResult =
  | { type: "number"; value: number }
  | { type: "string"; value: string }
  | { type: "boolean"; value: boolean }
  | { type: "error"; code: string }
  | { type: "blank" };
```

然后针对热路径拆函数：

```ts
function renderNumberResult(value: number) {}
function renderStringResult(value: string) {}
function renderErrorResult(code: string) {}
```

让每个函数的参数类型更稳定。

---

## 14.4 大数组 / 稀疏矩阵

表格天然是稀疏结构。不要为了表示大表格直接做：

```js
const cells = [];
cells[999999] = cell;
```

这很容易把数组推向稀疏表示。

更推荐：

```js
const cellMap = new Map(); // key: rowId:colId
```

或者：

```js
const chunks = new Map(); // 分块存储
```

再或者对数值密集区域使用：

```js
Float64Array
Int32Array
Uint32Array
```

这样比让普通 JS Array 在 packed / holey / dictionary 之间变化更稳定。

# 15. 如何观察 Deoptimization？

Node / V8 可以用这些 flag：

```bash
node --trace-opt --trace-deopt app.js
```

看数组 elements transition：

```bash
node --trace-elements-transitions app.js
```

开发实验可以用：

```bash
node --allow-natives-syntax app.js
```

然后在代码里：

```js
%OptimizeFunctionOnNextCall(fn);
%GetOptimizationStatus(fn);
```

典型输出里你会看到：

```txt
[optimizing ...]
[completed optimizing ...]
[bailout ... reason: wrong map]
[bailout ... reason: not a Smi]
[bailout ... reason: overflow]
[bailout ... reason: Insufficient type feedback]
```

常见 deopt reason 可以这样理解：

```txt
wrong map:
  对象 HiddenClass / shape 和优化时不一致

not a Smi:
  原来假设是小整数，结果不是

overflow:
  整数快路径溢出，需要回到 double / generic number 语义

wrong call target:
  原来内联 / 假设某个函数调用目标，后来变了

field-const:
  原来认为字段是稳定常量，后来被修改

out of bounds:
  数组访问越界，快路径不成立

hole:
  原来假设 packed array，后来遇到 holey array
```

---

# 16. 一个完整的心智模型

可以把 V8 的优化代码理解成这样：

```js
function optimizedGetX(obj) {
  if (obj.map !== ExpectedMap) {
    deopt();
  }

  return load(obj, offsetOfX);
}
```

或者：

```js
function optimizedAdd(a, b) {
  if (!isSmi(a)) deopt();
  if (!isSmi(b)) deopt();

  const result = intAdd(a, b);

  if (overflow(result)) deopt();

  return result;
}
```

所以所谓“优化代码退回去”，不是 V8 心血来潮，而是因为优化代码里本来就埋了很多 guard：

```txt
类型 guard
Map guard
ElementsKind guard
Bounds guard
Overflow guard
Prototype guard
Call target guard
Dependency guard
```

这些 guard 是优化成立的前提。

只要 guard 失败，就必须退。

# 17. 如何减少 deopt？实践清单

## 17.1 保持类型稳定

```js
// 不推荐
let value = 1;
value = "1";
value = {};
```

```js
// 推荐
let numericValue = 1;
let stringValue = "1";
let objectValue = {};
```

---

## 17.2 保持对象结构稳定

```js
// 推荐
function createCell() {
  return {
    row: 0,
    col: 0,
    value: null,
    formula: null,
    style: null,
    flags: 0,
  };
}
```

---

## 17.3 避免热路径 delete

```js
// 不推荐
delete cell.style;
```

```js
// 推荐
cell.style = null;
```

---

## 17.4 避免热路径动态加字段

```js
// 不推荐
if (needDebug) {
  cell.debugInfo = info;
}
```

```js
// 推荐
cell.debugInfo = null;
// 后续只更新值，不改变 shape
cell.debugInfo = info;
```

---

## 17.5 数组保持元素类型稳定

```js
// 不推荐
const arr = [1, 2, 3];
arr.push("4");
arr.push({});
```

```js
// 推荐
const numberArr = [1, 2, 3];
const objectArr = [{ value: 4 }];
```

---

## 17.6 高频数值计算考虑 TypedArray

```js
const values = new Float64Array(rowCount);
```

适合：

```txt
公式计算中间结果
稠密数值区域
布局坐标
行高列宽
滚动位置缓存
```

---

## 17.7 热函数不要过度泛化

不好：

```js
function process(value) {
  if (typeof value === "number") {}
  else if (typeof value === "string") {}
  else if (Array.isArray(value)) {}
  else if (value && typeof value === "object") {}
}
```

更好：

```js
function processNumber(value) {}
function processString(value) {}
function processArray(value) {}
function processObject(value) {}
```

让热点函数单态化。

---

## 17.8 不要在 Array 高阶函数 callback 中改变数组结构

不好：

```js
arr.map((x, i) => {
  if (i === 0) arr.length = 1;
  return x * 2;
});
```

这类行为会破坏 V8 对数组 builtin 的优化假设，V8 官方也提到过改变数组 shape / length 可能导致 deoptimization loop，并影响后续内联策略。([V8][7])

# 关键总结

1. **Deoptimization 是 V8 speculative optimization 的安全阀。**

2. **优化代码不是通用 JS 代码，而是基于历史反馈生成的快路径机器码。**

3. **优化代码依赖很多假设：类型、HiddenClass、ElementsKind、调用目标、原型链、字段 const、Smi 范围等。**

4. **一旦假设失效，继续执行优化代码可能会算错，所以必须退回解释器 / baseline。**

5. **deopt 时，V8 会根据 FrameState / deopt metadata 重建解释器状态。**

6. **频繁 deopt 会造成性能抖动、JIT 编译浪费、主线程尖刺，严重时形成 deoptimization loop。**

7. **业务代码里要减少 deopt，核心是：类型稳定、对象结构稳定、数组元素类型稳定、调用目标稳定、热路径不要动态增删属性。**

8. **对表格这种大型前端应用，cell model、formula result、render object、稀疏矩阵、滚动热路径都要特别注意 shape 和类型稳定性。**
