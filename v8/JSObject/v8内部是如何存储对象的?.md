下面从 **V8 内部对象模型** 的角度，深度拆解：一个 JS object 在 V8 里到底怎么存、怎么访问、怎么优化、什么时候退化。

---

# 1. 先给核心结论：V8 中的 object 不是简单 HashMap

从 JS 语义看，object 像一个动态字典：

```js
const obj = {
  name: 'Tom',
  age: 18,
};

obj.city = 'Shenzhen';
delete obj.age;
```

但 V8 不会一开始就把它当普通 HashMap 存。因为 HashMap 灵活，但属性访问慢。V8 的核心目标是：

> 尽可能把动态 JS object 变成“接近静态结构体”的存储方式，让 `obj.x` 可以被优化成固定偏移量读取。

所以 V8 内部大概会把 object 拆成：

```txt
JSObject
├── Map / HiddenClass        // 描述对象形状：有哪些属性、属性顺序、属性偏移、elements kind
├── properties               // 命名属性的额外 backing store
├── elements                 // 数字索引属性的 backing store，比如 obj[0]、array[1]
└── in-object properties     // 直接内嵌在对象里的属性槽，最快
```

V8 官方文档明确区分了 **named properties** 和 **elements**：普通命名属性进入 properties 体系，整数索引属性进入 elements 体系，两者是不同的数据结构；每个 JS object 还会关联一个 HiddenClass，用来描述对象形状。([V8][1])

---

# 2. V8 object 的第一层：Tagged Value

在 JS 层面你写：

```js
const obj = { x: 1 };
```

变量 `obj` 里并不是直接放整个对象，而是放一个 **Tagged Value**。

V8 中一个 JS 值通常分两类：

```txt
Tagged Value
├── Smi：Small Integer，小整数，直接编码在 value 里
└── HeapObject pointer：指向堆对象的指针，比如 Object、String、Array、Function、HeapNumber
```

例如：

```js
const a = 1;        // 可能是 Smi，直接存在 tagged value 中
const b = 1.1;      // 通常是 HeapNumber，堆上分配
const o = { x: 1 }; // tagged pointer，指向 JSObject
```

V8 使用 tag bits 来区分 Smi 和堆对象指针；小整数可以直接存在 tagged value 中，不需要额外堆分配。64 位架构下，V8 还引入了 pointer compression，用 32 位偏移表示堆对象地址，把对象放在 4GB pointer compression cage 内，从而减少指针内存占用。([V8][2])

所以从内存角度看：

```txt
变量 obj
└── tagged pointer
    └── JSObject in V8 heap
```

# 3. JSObject 的简化内存布局

一个普通 JS object 可以理解成下面这样：

```txt
JSObject
+-------------------------+
| Map pointer             |  -> HiddenClass / Shape / Map
+-------------------------+
| properties pointer      |  -> PropertyArray / NameDictionary / EmptyFixedArray
+-------------------------+
| elements pointer        |  -> FixedArray / FixedDoubleArray / NumberDictionary
+-------------------------+
| in-object property #0   |  -> obj.a
+-------------------------+
| in-object property #1   |  -> obj.b
+-------------------------+
| in-object property #2   |  -> obj.c
+-------------------------+
```

以这个对象为例：

```js
const obj = {
  a: 1,
  b: 'hello',
};

obj[0] = 'zero';
```

内部可以近似理解为：

```txt
obj JSObject
├── Map
│   ├── instance_type: JS_OBJECT_TYPE
│   ├── in-object property count: 2
│   ├── descriptor array:
│   │   ├── a -> in-object slot 0
│   │   └── b -> in-object slot 1
│   └── elements kind: PACKED_ELEMENTS / HOLEY_ELEMENTS ...
│
├── properties
│   └── empty / extra named properties backing store
│
├── elements
│   └── index 0 -> 'zero'
│
├── in-object slot 0
│   └── Smi(1)
│
└── in-object slot 1
    └── pointer -> String('hello')
```

注意：

```js
obj.a
```

和：

```js
obj[0]
```

在 V8 内部不是同一套存储路径。

`obj.a` 是 **named property**。

`obj[0]` 是 **element / indexed property**。

这也是为什么 V8 会专门为数组、类数组、稀疏数组设计 elements kind 体系。

# 4. Map / HiddenClass：object 存储的灵魂

V8 里的 **Map** 不是 JS 的 `Map` 对象，而是对象的隐藏类，也叫：

```txt
Map / HiddenClass / Shape
```

它描述的是：

```txt
这个对象长什么样？
有哪些属性？
属性按什么顺序添加？
每个属性存在对象内，还是 properties backing store？
每个属性的 offset 是多少？
这个对象的 prototype 是什么？
elements kind 是什么？
对象大小是多少？
是否可扩展？
字段类型倾向是什么？
```

官方 Hidden Class 文档中提到，Map 会记录对象的属性列表以及每个属性的精确位置；V8 依靠 Hidden Class 和 Inline Cache 来从运行时对象中学习结构。([V8][3])

举个例子：

```js
function Point(x, y) {
  this.x = x;
  this.y = y;
}

const p1 = new Point(1, 2);
const p2 = new Point(3, 4);
```

V8 可能会形成这样的 Map transition chain：

```txt
Empty Map
   |
   | add x
   v
Map1: { x }
   |
   | add y
   v
Map2: { x, y }
```

`p1` 和 `p2` 如果属性添加顺序一致，就可以共享同一个最终 Map：

```txt
p1.map ---> Map2
p2.map ---> Map2
```

这意味着 V8 可以知道：

```js
p.x
```

就是：

```txt
检查 p.map === Map2
然后读取 offset 0
```

所以属性访问可以从“查字典”变成“固定偏移读取”。

# 5. 为什么属性添加顺序很重要？

看这两个对象：

```js
const a = {};
a.x = 1;
a.y = 2;

const b = {};
b.y = 2;
b.x = 1;
```

虽然 JS 层面它们最终都有 `x` 和 `y`，但 V8 眼里它们的结构不同：

```txt
a:
Empty -> add x -> add y

b:
Empty -> add y -> add x
```

也就是：

```txt
a.map !== b.map
```

对象结构相同且属性顺序相同时，会共享 HiddenClass；默认情况下，每新增一个 named property，V8 会创建一个新的 HiddenClass；添加 array-indexed property 不会创建新的 HiddenClass。([V8][1])

这直接影响 Inline Cache：

```js
function getX(o) {
  return o.x;
}
```

如果传入对象 shape 稳定：

```js
getX({ x: 1, y: 2 });
getX({ x: 3, y: 4 });
getX({ x: 5, y: 6 });
```

V8 可以把它优化成：

```txt
if (o.map === ExpectedMap) {
  return o[in-object-offset-0];
}
```

如果传入对象 shape 混乱：

```js
getX({ x: 1, y: 2 });
getX({ y: 2, x: 1 });
getX({ x: 1, z: 3 });
getX(Object.create(null));
```

Inline Cache 会从：

```txt
monomorphic
```

退化到：

```txt
polymorphic
```

甚至：

```txt
megamorphic
```

最终访问路径变慢。

# 6. named properties 的三种存储方式

V8 对普通命名属性有三种主要存储方式：

```txt
named properties
├── in-object properties
├── fast properties
└── slow / dictionary properties
```

V8 官方文档明确将 named properties 分成三类：in-object、fast、slow/dictionary。其中 in-object 直接存在对象内，是最快的；fast properties 存在 properties store 中，通过 descriptor array 定位；slow properties 存在自包含字典里，灵活但访问更慢。([V8][1])

---

## 6.1 in-object properties：最快

例如：

```js
function User(id, name) {
  this.id = id;
  this.name = name;
}

const u = new User(1, 'Tom');
```

如果 V8 预测 `User` 实例大概率有两个字段：

```txt
id
name
```

它会尽量把它们存在对象内部：

```txt
User instance
+---------------------+
| Map                 |
+---------------------+
| properties          |
+---------------------+
| elements            |
+---------------------+
| id                  |  <- in-object slot 0
+---------------------+
| name                |  <- in-object slot 1
+---------------------+
```

访问：

```js
u.id
```

可以变成：

```txt
check map
load [object + fixed_offset]
```

这是最快路径。

---

## 6.2 fast properties：多一层间接访问

如果属性太多，超过对象内部预留空间，后续属性可能会放到 properties backing store：

```js
const obj = {};
obj.a = 1;
obj.b = 2;
obj.c = 3;
obj.d = 4;
obj.e = 5;
```

可能变成：

```txt
JSObject
├── in-object:
│   ├── a
│   └── b
└── properties backing store:
    ├── c
    ├── d
    └── e
```

访问 `obj.d` 时：

```txt
1. 检查 obj.map
2. 通过 descriptor array 知道 d 在 properties[1]
3. 读取 obj.properties[1]
```

比 in-object 多一次指针跳转，但仍然是 fast property。

---

## 6.3 slow / dictionary properties：退化成字典

如果对象频繁增删属性：

```js
const obj = {};

for (let i = 0; i < 1000; i++) {
  obj['key_' + i] = i;
}

delete obj.key_1;
delete obj.key_2;
```

V8 可能不再维护复杂的 HiddenClass transition tree，而是把 properties 转为 dictionary mode：

```txt
properties -> NameDictionary / SwissNameDictionary
```

大概类似：

```txt
{
  key_0: { value: 0, attributes: ... },
  key_3: { value: 3, attributes: ... },
  ...
}
```

这样新增、删除属性更灵活，但访问变慢，因为 Inline Cache 很难再把它优化成稳定 offset。V8 官方也说明，dictionary properties 不再通过 HiddenClass 共享元信息，并且 inline caches 不适用于 dictionary properties，所以通常比 fast properties 慢。([V8][1])

# 7. DescriptorArray：属性名到存储位置的映射表

Map 本身不会直接存所有属性值，它主要存结构信息。

对于 fast properties，Map 会指向一个 DescriptorArray：

```txt
Map
└── DescriptorArray
    ├── descriptor 0: name = "x", details = ..., location = in-object slot 0
    ├── descriptor 1: name = "y", details = ..., location = in-object slot 1
    └── descriptor 2: name = "z", details = ..., location = properties[0]
```

每个 descriptor 大概描述：

```txt
property name
property attributes: writable / enumerable / configurable
property kind: data / accessor
location: in-object / properties store
field index / offset
field representation: Smi / Double / Tagged / HeapObject ...
```

例如：

```js
const p = { x: 1, y: 2 };
```

可以理解为：

```txt
Map2
└── DescriptorArray
    ├── x -> in-object slot 0
    └── y -> in-object slot 1
```

对象值本身在对象里：

```txt
p
├── slot 0: Smi(1)
└── slot 1: Smi(2)
```

Map 负责回答：

```txt
x 在哪里？
y 在哪里？
```

对象负责存：

```txt
x 的值是什么？
y 的值是什么？
```

# 8. elements：数字索引属性单独存

看这个对象：

```js
const obj = {};
obj.name = 'Tom';
obj[0] = 'zero';
obj[1] = 'one';
```

V8 不会把 `0`、`1` 和 `name` 放到同一个 properties store 里，而是拆开：

```txt
JSObject
├── named properties
│   └── name -> 'Tom'
└── elements
    ├── 0 -> 'zero'
    └── 1 -> 'one'
```

官方文档说明：indexed properties 始终单独保存在 elements store 中；elements 也有 fast/dictionary 等不同表示。([V8][1])

数组也是对象，只是它的 elements 更重要：

```js
const arr = [1, 2, 3];
```

可以理解成：

```txt
JSArray
├── Map
├── properties
├── elements -> FixedArray / FixedDoubleArray
└── length
```

其中：

```txt
arr[0]
arr[1]
arr[2]
```

主要存在 elements backing store。

# 9. elements kind：数组性能的关键

V8 会根据数组内容给 elements 分类型。

常见 elements kind：

```txt
PACKED_SMI_ELEMENTS       // 连续小整数
HOLEY_SMI_ELEMENTS        // 有洞的小整数数组
PACKED_DOUBLE_ELEMENTS    // 连续 double 数组
HOLEY_DOUBLE_ELEMENTS     // 有洞的 double 数组
PACKED_ELEMENTS           // 普通对象/字符串/混合值
HOLEY_ELEMENTS            // 有洞的普通数组
DICTIONARY_ELEMENTS       // 稀疏数组
```

例如：

```js
const a = [1, 2, 3];
// PACKED_SMI_ELEMENTS

a.push(4.5);
// PACKED_DOUBLE_ELEMENTS

a.push('hello');
// PACKED_ELEMENTS
```

再比如：

```js
const arr = [1, 2, 3];
arr[10] = 99;
```

中间出现洞：

```txt
index 3 ~ 9 are holes
```

可能从：

```txt
PACKED_SMI_ELEMENTS
```

退化为：

```txt
HOLEY_SMI_ELEMENTS
```

V8 官方 elements kind 文档说明：V8 会跟踪数组元素类型，从而为 `map`、`reduce`、`forEach` 等数组操作选择更具体的优化路径；packed 数组比 holey 数组更容易优化，holey 数组需要额外检查和原型链查找。([V8][4])

# 10. packed vs holey：为什么数组“洞”很伤？

```js
const arr = [1, 2, 3];
```

这是 packed：

```txt
index:  0  1  2
value:  1  2  3
```

访问：

```js
arr[1]
```

V8 很容易知道：

```txt
直接读 elements[1]
```

但如果：

```js
const arr = [1, , 3];
```

这是 holey：

```txt
index:  0     1      2
value:  1   <hole>   3
```

访问：

```js
arr[1]
```

不能简单返回 `undefined`，因为 JS 原型链可能有这个属性：

```js
Array.prototype[1] = 'from prototype';

const arr = [1, , 3];
console.log(arr[1]); // 可能读到 prototype 上的值
```

所以 holey elements 需要：

```txt
1. 检查 elements[1] 是否是 hole
2. 如果是 hole，继续查 prototype chain
3. 处理 accessor / descriptor / proxy 等情况
```

这比 packed 慢。

V8 文档也提到，holey elements 需要额外检查和原型链查找，而 packed elements 可以执行更局部、更高效的操作。([V8][1])

# 11. Smi、HeapNumber、MutableHeapNumber 与对象字段

对象属性值本身也有不同表示。

```js
const obj = {
  x: 42,
  y: 4.2,
};
```

V8 可能这样存：

```txt
obj.x -> Smi(42)
obj.y -> pointer -> HeapNumber(4.2)
```

V8 官方文章说明：ECMAScript 层面的 number 是 Float64 语义，但引擎不会永远用 Float64 存储；V8 对小整数使用 Smi，不在 Smi 范围内或不能用 Smi 表示的数字使用 HeapNumber。([V8][5])

比如：

```txt
42      -> Smi
0       -> Smi
-0      -> HeapNumber
4.2     -> HeapNumber
NaN     -> HeapNumber
Infinity -> HeapNumber
```

对于对象字段，V8 还会记录字段 representation：

```txt
field x: Smi
field y: Double
field z: Tagged
```

看这个例子：

```js
const a = { x: 1 };
const b = { x: 2 };

b.x = 0.2;
```

一开始：

```txt
x: Smi representation
```

后来 `b.x = 0.2`，字段需要从 Smi 变成 Double。V8 可能创建新的 shape，把字段 representation 改成 Double，并让相关对象迁移到新的 shape。官方 React 性能悬崖文章详细解释了 Smi、HeapNumber、MutableHeapNumber、字段 representation 变化、shape deprecation 和 migration 的过程。([V8][5])

这也是为什么热路径对象字段最好不要频繁混类型：

```js
// 不推荐
const node = {
  startTime: null,
};

node.startTime = performance.now(); // 后面变成 double
```

更好：

```js
const node = {
  startTime: Number.NaN,
};

node.startTime = performance.now();
```

当然，这是 V8 层面的性能优化思路，业务代码要优先保证可读性和语义正确。

# 12. Object 属性访问全过程

以：

```js
function readX(o) {
  return o.x;
}
```

为例。

第一次执行：

```js
readX({ x: 1, y: 2 });
```

V8 一开始可能走通用路径：

```txt
1. 读取 o.map
2. 在 Map 的 DescriptorArray 中查找 x
3. 找到 x 的位置：in-object slot 0
4. 读取 slot 0
5. 把这次反馈记录到 Inline Cache / feedback vector
```

多次执行后，如果发现传进来的对象 Map 稳定：

```js
readX({ x: 1, y: 2 });
readX({ x: 3, y: 4 });
readX({ x: 5, y: 6 });
```

V8 可以优化成：

```txt
if (o.map === ExpectedMap) {
  return o.slot0;
} else {
  fallback_to_generic_lookup();
}
```

机器码层面接近：

```txt
cmp [object + map_offset], expected_map
jne slow_path
mov result, [object + property_offset]
```

这就是 HiddenClass + Inline Cache 的意义。

V8 官方 fast properties 文档也明确提到，HiddenClass 是优化编译器和 inline caches 的重要基础，优化编译器可以在确认对象结构兼容时直接 inline 属性访问。([V8][1])

# 13. prototype chain 怎么参与对象存储？

看这个例子：

```js
const proto = { y: 2 };
const obj = Object.create(proto);
obj.x = 1;

console.log(obj.y);
```

`obj.y` 不在自身对象上。

访问过程大概是：

```txt
1. 查 obj 自身 Map / DescriptorArray
2. 没找到 y
3. 读取 obj.[[Prototype]]
4. 查 proto 的 Map / DescriptorArray
5. 找到 y
6. 返回 proto.y
```

所以一个属性读取不只是查当前对象，还可能查：

```txt
object
 -> prototype
   -> prototype's prototype
     -> Object.prototype
       -> null
```

V8 会尽量通过 Map、prototype validity cell、IC guard 等机制优化原型链访问。但如果你动态改 prototype：

```js
Object.setPrototypeOf(obj, newProto);
```

或者修改原型上的属性结构，就可能让相关优化失效。

# 14. delete 为什么容易让对象变慢？

看这个例子：

```js
const obj = {
  a: 1,
  b: 2,
  c: 3,
};

delete obj.b;
```

从 JS 语义看，只是删了一个属性。

但从 V8 视角看，这会破坏稳定 shape：

```txt
Map: { a, b, c }
```

删除后变成：

```txt
Map: { a, c }
```

如果频繁 add/delete，维护 HiddenClass transition tree 的收益就变低。V8 可能把对象转成 dictionary properties：

```txt
fast properties -> dictionary properties
```

这样删除、新增更容易，但属性访问慢。

所以热路径上，通常不建议：

```js
delete obj.x;
```

可以考虑：

```js
obj.x = undefined;
```

或者：

```js
obj.x = null;
```

当然，如果业务语义必须区分“属性不存在”和“属性值为 undefined”，那就不能随便替换。

# 15. Object.freeze / seal / preventExtensions 对 Map 的影响

这些 API 会改变对象的 extensibility / integrity level：

```js
Object.preventExtensions(obj);
Object.seal(obj);
Object.freeze(obj);
```

它们不只是设置一个普通属性，而是会让对象进入特殊 shape：

```txt
extensible Map
   |
   | preventExtensions
   v
non-extensible Map
```

React 的 V8 性能悬崖案例里就涉及：

```js
Object.preventExtensions(this);
```

再加上字段从 Smi 变 Double，导致 shape transition/migration 复杂化。V8 官方文章提到，对象阻止扩展会进行特殊 transition，字段 representation 变化又会引发 shape deprecation 和 migration。([V8][5])

所以在极端性能敏感路径上，`freeze/seal/preventExtensions` 不一定总是免费优化。它们更多是语义工具，不应无脑用于性能优化。

# 16. 普通 object 和 Map 数据结构的选择

如果你是做“固定结构数据”：

```js
const user = {
  id: 1,
  name: 'Tom',
  age: 18,
};
```

普通 object 非常适合。V8 可以用 HiddenClass 优化。

如果你是做“动态字典”：

```js
const cache = {};
cache[userInputKey] = value;
delete cache[oldKey];
```

尤其 key 很动态、频繁增删，普通 object 可能会进入 dictionary mode。

这时更适合：

```js
const cache = new Map();

cache.set(userInputKey, value);
cache.delete(oldKey);
```

因为 JS `Map` 语义上就是为动态 key-value 容器设计的，不依赖对象 shape 稳定性。

简单判断：

```txt
固定字段结构：Object / class instance
动态 key-value：Map
大量数值索引：Array / TypedArray
稀疏数值索引：Map / 自定义稀疏结构
```

# 17. class 对象怎么存？

```js
class Point {
  constructor(x, y) {
    this.x = x;
    this.y = y;
  }

  length() {
    return Math.sqrt(this.x * this.x + this.y * this.y);
  }
}
```

实例对象：

```js
const p = new Point(3, 4);
```

大概是：

```txt
p JSObject
├── Map
├── properties
├── elements
├── in-object x
└── in-object y
```

方法 `length` 不在实例对象上，而在 prototype 上：

```txt
Point.prototype.length
```

所以：

```js
p.length()
```

访问过程是：

```txt
1. p 自身找 length
2. 没找到
3. 去 Point.prototype 找
4. 找到 function
5. 调用，this = p
```

这也是为什么 class 方法不会为每个实例重复创建一份，内存更友好。

对比：

```js
class Point {
  constructor(x, y) {
    this.x = x;
    this.y = y;

    this.length = function () {
      return Math.sqrt(this.x * this.x + this.y * this.y);
    };
  }
}
```

这里每个实例都有自己的 `length` 函数对象：

```txt
p1.length !== p2.length
```

内存会更重。

# 18. 对象字面量的存储过程

```js
const obj = {
  a: 1,
  b: 2,
};
```

V8 不一定真的逐个执行：

```js
const obj = {};
obj.a = 1;
obj.b = 2;
```

对于 object literal，V8 会有 boilerplate / literal feedback 等机制，尽量快速克隆出相同 shape 的对象。

但从最终存储结果看，仍然可以理解为：

```txt
Map: { a, b }
in-object slot 0: 1
in-object slot 1: 2
```

如果每次字面量结构稳定：

```js
function createUser(id, name) {
  return {
    id,
    name,
    age: 0,
  };
}
```

V8 很容易优化。

如果结构不稳定：

```js
function createUser(type) {
  const obj = {};

  if (type === 'a') {
    obj.id = 1;
    obj.name = 'Tom';
  } else {
    obj.name = 'Tom';
    obj.id = 1;
  }

  return obj;
}
```

最终对象字段一样，但添加顺序不同，可能形成不同 Map。

# 19. 大对象、多对象场景下的内存问题

假设你在表格系统里有几百万个 cell：

```js
const cell = {
  row: 1,
  col: 2,
  value: 'hello',
  formula: null,
  style: null,
  comment: null,
  validation: null,
};
```

如果每个 cell 都是完整对象，会有明显开销：

```txt
每个 cell:
├── JSObject header
├── Map pointer
├── properties pointer
├── elements pointer
├── 多个属性槽
├── 字符串/对象引用
└── 额外 HeapObject
```

几百万个对象时，问题会非常明显：

```txt
对象头开销
属性槽开销
指针开销
GC 扫描成本
shape 多态
字符串重复
可选字段浪费
```

更好的设计通常是：

```txt
1. 热字段固定化
2. 冷字段拆出去
3. 稀有字段 side table 化
4. 数值字段 TypedArray 化
5. 字符串池化 / ID 化
6. 避免为每个单元格创建完整对象
```

例如：

```js
// 不一定适合海量场景
const cells = [
  { row: 0, col: 0, value: 'A1', style: null },
  { row: 0, col: 1, value: 'B1', style: null },
];
```

可以改成：

```js
const rows = new Uint32Array(count);
const cols = new Uint32Array(count);
const valueIds = new Uint32Array(count);
const styleIds = new Uint32Array(count);
```

或者：

```js
const cellMeta = new Map(); // 只存有特殊元信息的 cell
```

这本质上是从：

```txt
Array of Objects
```

转成：

```txt
Struct of Arrays
```

可以显著减少对象数量、指针数量和 GC 压力。

# 20. GC 视角：对象存储为什么影响回收？

V8 GC 扫描对象时，需要知道对象里哪些字段是指针，哪些不是。

对于普通 JSObject：

```txt
Map
properties pointer
elements pointer
in-object fields
```

很多字段可能是 tagged pointer，需要 GC 追踪。

但如果是 Smi：

```txt
Smi(42)
```

它不是堆对象，GC 不需要继续追踪。

如果是 packed Smi array：

```js
const arr = [1, 2, 3, 4];
```

元素都是 Smi，GC 压力很小。

如果是对象数组：

```js
const arr = [{}, {}, {}, {}];
```

每个元素都是 HeapObject pointer，GC 需要继续追踪这些对象。

V8 fast properties 文档也提到，Smi elements 中整数直接内联编码，GC 不需要像追踪对象引用一样查看这些元素；纯 double 数组还会使用 raw doubles 来避免额外内存和性能开销。([V8][1])

所以：

```js
const arr = [1, 2, 3];
```

和：

```js
const arr = [{ value: 1 }, { value: 2 }, { value: 3 }];
```

GC 成本完全不同。

# 21. 从 V8 object 存储推导出的最佳实践

## 21.1 固定对象结构

推荐：

```js
class Cell {
  constructor(row, col, value) {
    this.row = row;
    this.col = col;
    this.value = value;
    this.formula = null;
    this.style = null;
  }
}
```

不推荐：

```js
const cell = {};

if (hasValue) cell.value = value;
if (hasFormula) cell.formula = formula;
if (hasStyle) cell.style = style;
```

原因：

```txt
前者 shape 稳定
后者 shape 分支多
```

---

## 21.2 属性添加顺序保持一致

推荐：

```js
function createUser(id, name, age) {
  return {
    id,
    name,
    age,
  };
}
```

不推荐：

```js
function createUser(data) {
  const user = {};

  if (data.name) user.name = data.name;
  if (data.id) user.id = data.id;
  if (data.age) user.age = data.age;

  return user;
}
```

---

## 21.3 热路径避免 delete

不推荐：

```js
delete obj.x;
```

可考虑：

```js
obj.x = undefined;
```

原因：

```txt
delete 容易破坏 fast properties
频繁 delete 可能进入 dictionary mode
```

---

## 21.4 动态字典用 Map

推荐：

```js
const dict = new Map();

dict.set(key, value);
dict.delete(key);
```

不推荐：

```js
const dict = {};
dict[key] = value;
delete dict[key];
```

尤其 key 来自用户输入、数量大、频繁增删时。

---

## 21.5 数组保持 packed

推荐：

```js
const arr = [];

for (let i = 0; i < n; i++) {
  arr.push(i);
}
```

避免：

```js
const arr = [];
arr[100000] = 1;
```

避免：

```js
delete arr[1];
```

可以用：

```js
arr[1] = undefined;
```

但要注意语义差异。

---

## 21.6 数值数组考虑 TypedArray

如果你存的是大量数字：

```js
const values = new Float64Array(count);
```

比：

```js
const values = new Array(count).fill(0).map(v => ({ value: v }));
```

更省内存、更少 GC、更贴近底层连续内存。

---

## 21.7 字段类型尽量稳定

不推荐：

```js
const item = {
  count: null,
};

item.count = 1;
item.count = 1.5;
item.count = 'unknown';
```

推荐：

```js
const item = {
  count: 0,
};
```

或者如果后面一定是 double：

```js
const item = {
  time: Number.NaN,
};
```

字段类型稳定，有利于 V8 做 representation tracking。

---

# 22. 一句话串起完整链路

以：

```js
const obj = { x: 1, y: 2 };
console.log(obj.x);
```

为例，V8 内部大致是：

```txt
1. obj 是一个 tagged pointer，指向堆上的 JSObject
2. JSObject 第一个字段指向 Map / HiddenClass
3. Map 描述对象 shape：有 x、y，顺序是 x -> y
4. x、y 可能存在 in-object slots
5. obj.x 第一次访问走通用查找
6. V8 在 Inline Cache 中记录：这个 Map 的 x 在 slot 0
7. 后续如果传入相同 Map 的对象，直接 map check + offset load
8. 如果对象 shape 混乱、delete、动态属性过多，则可能退化为 polymorphic / megamorphic / dictionary mode
```

# 关键总结

V8 存储 object 的核心不是“字典”，而是：

```txt
JSObject + Map/HiddenClass + properties + elements + in-object slots
```

最重要的几个点：

1. **对象第一个核心字段是 Map / HiddenClass**，它描述对象形状，不存具体业务值。

2. **named properties 和 indexed elements 分开存**，`obj.x` 和 `obj[0]` 不是同一套结构。

3. **最快的是 in-object properties**，属性直接内嵌在对象里，可以通过固定 offset 访问。

4. **fast properties 通过 properties backing store 存储**，仍然可以借助 HiddenClass + DescriptorArray 快速定位。

5. **频繁增删属性会进入 dictionary mode**，更灵活但更慢，Inline Cache 优化效果差。

6. **数组由 elements kind 决定性能**，packed Smi array 最容易优化，holey/sparse/mixed array 更慢。

7. **属性添加顺序决定 HiddenClass 是否共享**，同字段但不同添加顺序，也可能生成不同 Map。

8. **对象字段类型也会影响存储**，Smi、HeapNumber、Double representation、Tagged representation 都会影响性能和 GC。

9. **大量对象场景要关注对象头、属性槽、指针、GC 扫描成本**，表格/编辑器/协同文档类业务尤其要避免“百万级小对象 + 大量可选字段”的设计。

10. **工程最佳实践**：固定结构、固定顺序、少 delete、动态 key 用 Map、数值密集用 TypedArray、热字段和冷字段拆分。
