下面我们系统学习 **V8 的内联缓存 Inline Cache，简称 IC**。你可以把它理解成 V8 把 JavaScript 动态对象访问“静态化”的关键机制之一。

---

# 1. 一句话理解 Inline Cache

**Inline Cache 的本质：**

> 在某个固定代码位置，V8 观察这个位置过去访问过什么对象形状，然后缓存“对象形状 → 属性访问路径”，下次再执行到同一个位置时，先检查对象形状是否匹配，匹配就直接按偏移量读写，避免重新走完整的动态属性查找流程。

比如：

```js
function getX(obj) {
  return obj.x;
}

getX({ x: 1, y: 2 });
getX({ x: 3, y: 4 });
```

如果两次传入对象的结构一致，V8 可以认为：

```txt
getX 函数里的 obj.x 这个访问点：
如果 obj 的 Map/HiddenClass 是 M1，
那么 x 一定位于 offset = 某个固定位置。
```

于是后续 `obj.x` 可以近似变成：

```txt
if (obj.map === M1) {
  return obj[offset_of_x];
} else {
  fallback_to_generic_lookup();
}
```

注意：**IC 缓存的不是 `x` 的值，而是 `x` 的访问方式。**

---

# 2. 为什么 JavaScript 需要 IC？

JavaScript 是动态语言。下面这行代码在静态阶段其实很难确定访问成本：

```js
obj.x
```

因为运行时可能发生很多事情：

```js
obj = { x: 1 };
obj = Object.create({ x: 2 });
obj = new Proxy({}, {});
obj = { get x() { return 1; } };
delete obj.x;
obj.__proto__.x = 10;
```

如果没有优化，每次访问 `obj.x` 都可能需要：

```txt
1. 判断 obj 是否为对象
2. 查找自身属性
3. 判断属性描述符
4. 判断 accessor / data property
5. 如果自身没有，查原型链
6. 如果有 getter，调用 getter
7. 如果对象是 Proxy，走 trap
8. 返回结果
```

这太慢。

所以 V8 的思路是：

> 大多数真实业务代码虽然语义是动态的，但运行时行为通常很稳定。
> 如果某个位置一直访问相同形状的对象，就可以把动态查找变成快速路径。

V8 官方文档也强调，理解属性内部表示是理解 V8 中 Inline Cache 等优化的基础；对象的 named properties、elements、HiddenClass/Map 都会参与属性访问优化。([V8][1])

---

# 3. IC 与 HiddenClass / Map 的关系

你前面已经学习过 V8 对象存储，这里把它和 IC 串起来。

在 V8 中，每个 JS 对象都会关联一个 HiddenClass，也常被称为 **Map**。这个 Map 描述对象的结构，包括：

```txt
对象有哪些属性？
属性添加顺序是什么？
属性在对象内还是 properties backing store 中？
属性对应的 offset / field index 是多少？
原型是谁？
```

V8 官方说明：HiddenClass 存储对象形状信息，并包含从属性名到属性存储位置的映射；HiddenClass 是优化编译器和 Inline Cache 的关键输入。([V8][1])

比如：

```js
const a = { x: 1, y: 2 };
const b = { x: 3, y: 4 };
```

如果属性相同、添加顺序相同，`a` 和 `b` 很可能共享同一个 Map：

```txt
a.map === b.map
```

那么 `getX(a)` 和 `getX(b)` 里的 `obj.x` 可以共享同一条 IC 快路径。

但是：

```js
const a = { x: 1, y: 2 };
const b = { y: 4, x: 3 };
```

虽然看起来都有 `x` 和 `y`，但添加顺序不同，V8 可能生成不同的 Map。V8 官方明确提到：**相同属性、相同顺序的对象共享同一个 HiddenClass；每新增一个 named property，默认都会产生新的 HiddenClass transition。**([V8][1])

# 4. 没有 IC 时，属性访问怎么走？

看代码：

```js
function getName(user) {
  return user.name;
}
```

第一次执行：

```js
getName({ name: 'Alice', age: 18 });
```

V8 不知道这个访问点稳定不稳定，所以要走比较通用的查找逻辑：

```txt
user.name
  ↓
检查 user 的 Map
  ↓
查 DescriptorArray
  ↓
找到 name 对应的 field index
  ↓
判断属性是在 in-object，还是 properties backing store
  ↓
读取值
```

在 V8 里，named properties 可能存在三种主要形态：

```txt
1. in-object properties
2. fast properties in properties store
3. slow / dictionary properties
```

官方文档说明：**in-object properties 直接存储在对象自身上，是最快的；fast properties 通过 properties store 和 HiddenClass 的 DescriptorArray 访问；slow properties 使用自包含字典，访问更慢。**([V8][1])

---

# 5. 有 IC 后，属性访问怎么走？

第二次、第三次执行同一个访问点时：

```js
getName({ name: 'Bob', age: 20 });
getName({ name: 'Tom', age: 22 });
```

如果这些对象共享同一个 Map，V8 可以把 `user.name` 这个位置优化成：

```txt
LoadIC for user.name:

if (user.map === cachedMap) {
  return load_from_known_offset(user, offset_of_name);
}

return generic_property_lookup(user, 'name');
```

这个 `LoadIC` 就是 “Load Inline Cache”。

可以粗略理解成：

```js
// 概念示意，不是真实 JS 代码
function getName(user) {
  if (user.__map__ === Map_User_name_age) {
    return user[KNOWN_OFFSET_NAME];
  }
  return Runtime_GenericGetProperty(user, 'name');
}
```

此时，原本动态的属性查找被简化成：

```txt
Map check + offset load
```

这就是 IC 的核心收益。

# 6. 为什么叫 Inline Cache？

它叫 **Inline Cache**，不是因为“函数内联”，而是因为：

> 缓存信息绑定在某个具体代码位置，也就是某个 call site / property access site 附近。

例如：

```js
function f(obj) {
  return obj.x + obj.x;
}
```

这里有两个 `obj.x`，它们虽然文本一样，但在字节码里是两个不同的访问点：

```txt
return obj.x + obj.x
       ↑       ↑
      IC1     IC2
```

每个访问点都有自己的反馈信息。

这点非常关键。IC 是 **per call site / per access site** 的，不是全局按属性名缓存。

---

# 7. IC 缓存什么？

以 `obj.x` 为例，IC 可能记录：

```txt
1. 这个访问点见过哪些 receiver Map
2. 对应属性 x 的存储位置
3. 是 in-object field 还是 properties backing store
4. 是否需要查原型链
5. 是否是 accessor/getter
6. 是否是 elements access
7. 是否需要特殊 builtin handler
8. 当前 IC 状态：uninitialized / monomorphic / polymorphic / megamorphic
```

更准确地说，V8 会把运行时反馈放入函数相关的 **Feedback Vector**。V8 官方在 Sparkplug 文章中提到，Feedback Vector 存储 object shape data，并且很多操作都需要加载它。([V8][2])

所以你可以把 IC 理解成：

```txt
代码位置 + FeedbackSlot + Map/Handler 信息
```

# 8. IC 的几种核心类型

常见 IC 类型可以按操作分类理解。

## 8.1 LoadIC：读取命名属性

对应：

```js
obj.x
obj.name
obj.count
```

优化目标：

```txt
把 obj.x 从动态属性查找变成 Map check + offset load
```

---

## 8.2 StoreIC：写入命名属性

对应：

```js
obj.x = 1;
obj.name = 'Alice';
```

优化目标：

```txt
如果对象 Map 匹配，并且写入不会改变结构：
  直接写 offset

如果是新增属性：
  触发 Map transition，然后写入新位置
```

例如：

```js
function User(name) {
  this.name = name;
  this.age = 0;
}
```

如果构造过程稳定，`this.name = name` 和 `this.age = 0` 的 StoreIC 会很容易稳定。

但如果：

```js
function User(name, vip) {
  this.name = name;

  if (vip) {
    this.vip = true;
  }

  this.age = 0;
}
```

那么不同实例可能产生不同 Map：

```txt
普通用户: name → age
VIP用户: name → vip → age
```

这会影响后续 LoadIC/StoreIC 的稳定性。

V8 官方的 Indicium 案例中就展示了类似问题：一个 `Point` 类根据条件才添加 `isNegative`，导致同一类对象出现多个 Map，IC 从 monomorphic 变成 polymorphic，并造成性能差异；解决方案是始终在 constructor 中初始化该字段。([V8][3])

---

## 8.3 KeyedLoadIC：动态 key 读取

对应：

```js
obj[key]
arr[index]
```

这个比 `obj.x` 更复杂，因为 key 不是静态属性名。

例如：

```js
function get(obj, key) {
  return obj[key];
}
```

这个访问点可能见到：

```js
get(user, 'name');
get(user, 'age');
get(array, 0);
get(array, 1);
get(dict, dynamicKey);
```

如果 key 类型、对象形状、elements kind 都变化，这个 IC 很容易变成 polymorphic 或 megamorphic。

---

## 8.4 KeyedStoreIC：动态 key 写入

对应：

```js
obj[key] = value;
arr[index] = value;
```

数组场景里，KeyedStoreIC 和 elements kind 关系很大。

例如：

```js
const arr = [1, 2, 3];      // PACKED_SMI_ELEMENTS
arr[0] = 1.1;               // 可能转为 PACKED_DOUBLE_ELEMENTS
arr[1] = 'x';               // 可能转为 PACKED_ELEMENTS
delete arr[2];              // 可能变成 HOLEY
```

V8 官方文档说明，V8 会跟踪数组的 elements kind，并基于 elements kind 优化数组操作；如果同一函数处理多种 elements kind，就可能形成 polymorphic 操作，增加额外检查。([V8][4])

---

## 8.5 CallIC：函数调用缓存

对应：

```js
obj.method()
fn()
```

调用也需要缓存，因为 JS 中函数调用同样高度动态。

例如：

```js
function callRun(obj) {
  return obj.run();
}
```

这里至少有两步：

```txt
1. 读取 obj.run
2. 调用这个函数
```

如果 `obj.run` 每次都是同一个函数，或者少数几个稳定函数，V8 可以优化调用路径。

但如果：

```js
callRun({ run() {} });
callRun({ run: someOtherFn });
callRun(proxyObj);
callRun(objWithGetter);
```

调用点就可能快速变复杂。

# 9. IC 的状态机：从 Uninitialized 到 Megamorphic

IC 的状态可以概念化理解为：

```txt
Uninitialized
    ↓
Monomorphic
    ↓
Polymorphic
    ↓
Megamorphic
```

不同 V8 版本内部状态细节会有变化，但这个模型足够用于性能分析和面试表达。

---

## 9.1 Uninitialized：还没见过对象

第一次执行：

```js
function getX(o) {
  return o.x;
}

getX({ x: 1 });
```

此时 `o.x` 这个访问点还没有反馈信息：

```txt
IC state: Uninitialized
```

V8 会走通用路径，查出 `x` 的位置，同时记录这个对象的 Map 和访问 handler。

---

## 9.2 Monomorphic：只见过一种对象形状

如果后续一直传入同一种 Map：

```js
getX({ x: 1, y: 2 });
getX({ x: 3, y: 4 });
getX({ x: 5, y: 6 });
```

IC 进入：

```txt
IC state: Monomorphic
```

这是最理想状态。

访问路径：

```txt
check map M1
  ↓
load offset x
```

示意：

```txt
obj.x

Before:
  GenericLookup(obj, "x")

After:
  if obj.map == M1:
      return *(obj + offset_x)
  else:
      miss
```

---

## 9.3 Polymorphic：见过少量不同对象形状

比如：

```js
function getX(o) {
  return o.x;
}

getX({ x: 1, y: 2 });
getX({ x: 1, z: 3 });
```

两个对象都有 `x`，但 shape 不同：

```txt
Map1: x, y
Map2: x, z
```

IC 可能变成：

```txt
IC state: Polymorphic
```

访问路径变成：

```txt
if obj.map === M1:
  load offset_x_for_M1
else if obj.map === M2:
  load offset_x_for_M2
else:
  miss
```

这仍然比完全动态查找快，但比 monomorphic 慢，因为多了 Map 判断分支。

V8 官方 Indicium 案例也明确展示：IC 从 monomorphic 变成 polymorphic 后，需要跟踪多个 Map，并执行额外检查，性能更差。([V8][3])

---

## 9.4 Megamorphic：见过太多对象形状

如果同一个访问点见过大量不同 shape：

```js
function getX(o) {
  return o.x;
}

getX({ x: 1 });
getX({ a: 1, x: 1 });
getX({ b: 1, x: 1 });
getX({ c: 1, x: 1 });
getX({ d: 1, x: 1 });
getX({ e: 1, x: 1 });
```

V8 会认为：

```txt
这个访问点太不稳定了，不值得继续维护大量专用快路径。
```

于是进入：

```txt
IC state: Megamorphic
```

此时通常会退化为更通用的查找机制，例如 megamorphic stub/cache 或 generic lookup。

结果：

```txt
Monomorphic:   最快，1 个 Map check
Polymorphic:   还能优化，但多分支
Megamorphic:   优化价值下降，接近通用动态查找
```

V8 官方在 hash table 优化文章中也提到，monomorphic IC 在 key 拥有相同 hidden class 时很快，但真实代码中如果 keys 有不同 hidden classes，会导致慢的 megamorphic IC lookup。([V8][5])

# 10. IC 与 V8 执行流水线的关系

现在的 V8 不是只有一个执行层，而是多层：

```txt
JavaScript Source
  ↓
Parser
  ↓
Ignition Bytecode
  ↓
Ignition Interpreter
  ↓
Sparkplug Baseline Compiler
  ↓
Maglev Optimizing Compiler
  ↓
TurboFan Optimizing Compiler
```

V8 官方说明，JS 代码会先编译为 Ignition bytecode 并解释执行；执行期间 V8 会跟踪程序行为，包括对象形状和类型，这些运行时元数据会和 bytecode 一起输入优化编译器，用于生成高性能、带推测性质的机器码。([V8][6])

IC 在这个过程里的位置是：

```txt
运行时执行代码
  ↓
IC 收集反馈：这个位置见过哪些 Map / 类型 / elements kind
  ↓
Feedback Vector 保存这些信息
  ↓
Maglev / TurboFan 根据反馈生成优化代码
```

所以 IC 不只是“加速解释执行”，它还是优化编译器的重要情报来源。

---

# 11. IC 与 TurboFan / Maglev 的关系

假设有代码：

```js
function sumX(arr) {
  let sum = 0;

  for (let i = 0; i < arr.length; i++) {
    sum += arr[i].x;
  }

  return sum;
}
```

如果 `arr[i]` 总是同一种对象 shape：

```js
[
  { x: 1, y: 2 },
  { x: 3, y: 4 },
  { x: 5, y: 6 },
]
```

IC 收集到的信息是：

```txt
arr.length:
  array map 稳定

arr[i]:
  elements kind 稳定

arr[i].x:
  receiver map 稳定
  x offset 稳定
```

优化编译器就可以生成更激进的机器码：

```txt
1. 检查 arr 的 Map / elements kind
2. 循环中直接按 elements backing store 取元素
3. 检查元素对象 Map
4. 直接按 offset 取 x
5. 累加
```

但是如果数组里混入各种 shape：

```js
[
  { x: 1, y: 2 },
  { x: 3, z: 4 },
  { a: 1, x: 5 },
  new Proxy({ x: 1 }, {}),
]
```

IC 反馈就会变差，优化编译器只能生成更多分支，甚至放弃部分优化。

这就是为什么性能敏感代码里常说：

> 保持对象 shape 稳定，本质是在喂给 IC 和优化编译器更稳定的反馈。

# 12. 深入看一个例子：对象属性顺序如何影响 IC

## 12.1 好代码：对象 shape 一致

```js
function createUser(name, age) {
  return {
    name,
    age,
    score: 0,
  };
}

function getScore(user) {
  return user.score;
}

const u1 = createUser('A', 18);
const u2 = createUser('B', 20);

getScore(u1);
getScore(u2);
```

两个对象属性顺序一致：

```txt
name → age → score
```

所以大概率共享同一个 Map：

```txt
Map_User:
  name
  age
  score
```

`getScore` 里的 IC 很容易保持 monomorphic。

---

## 12.2 坏代码：属性顺序不一致

```js
const u1 = {
  name: 'A',
  age: 18,
  score: 0,
};

const u2 = {
  score: 0,
  name: 'B',
  age: 20,
};

function getScore(user) {
  return user.score;
}

getScore(u1);
getScore(u2);
```

虽然最终都有：

```txt
name, age, score
```

但添加顺序不同：

```txt
u1: name → age → score
u2: score → name → age
```

这可能产生两个不同 Map，`getScore` 变成 polymorphic。

# 13. 条件添加属性为什么伤 IC？

看代码：

```js
class Point {
  constructor(x, y) {
    if (x < 0 || y < 0) {
      this.isNegative = true;
    }

    this.x = x;
    this.y = y;
  }

  dot(other) {
    return this.x * other.x + this.y * other.y;
  }
}
```

这里的问题是：

```txt
正数点:
  x → y

负数点:
  isNegative → x → y
```

于是：

```txt
Point 实例出现两种 Map
```

当 `dot()` 中访问：

```js
this.x
this.y
other.x
other.y
```

IC 会发现同一个访问点见到了多个 Map，于是从 monomorphic 变成 polymorphic。

V8 官方 Indicium 案例正是这个模式：条件添加 `isNegative` 导致多 Map 和 IC polymorphic；修复方式是总是在 constructor 中初始化该属性。([V8][3])

更好的写法：

```js
class Point {
  constructor(x, y) {
    this.isNegative = x < 0 || y < 0;
    this.x = x;
    this.y = y;
  }

  dot(other) {
    return this.x * other.x + this.y * other.y;
  }
}
```

这样所有实例都是：

```txt
isNegative → x → y
```

IC 更稳定。

# 14. delete 为什么容易伤 IC？

```js
const user = {
  name: 'Alice',
  age: 18,
};

delete user.age;
```

`delete` 会破坏对象稳定结构。V8 为了支持频繁添加/删除属性，可能把对象从 fast properties 转成 slow/dictionary properties。

V8 官方说明，如果对象频繁添加和删除属性，维护 DescriptorArray 和 HiddenClass 会带来时间和内存成本，因此 V8 支持 slow properties；slow properties 把元信息放进 properties dictionary，不再通过 HiddenClass 共享，访问也更慢。([V8][1])

性能敏感代码中，通常建议：

```js
// 不推荐
delete user.age;

// 更推荐
user.age = null;
// 或
user.age = undefined;
```

原因不是 `undefined` 一定更优雅，而是：

```txt
保留对象 shape
  ↓
避免 Map 退化
  ↓
让 IC 继续稳定
```

# 15. 数组中的 IC：elements kind 也会被缓存

对象属性有 Map，数组元素也有自己的分类，也就是 **elements kind**。

比如：

```js
const a = [1, 2, 3];
```

可能是：

```txt
PACKED_SMI_ELEMENTS
```

如果变成：

```js
a.push(1.1);
```

可能转成：

```txt
PACKED_DOUBLE_ELEMENTS
```

如果再变成：

```js
a.push('x');
```

可能转成：

```txt
PACKED_ELEMENTS
```

如果：

```js
delete a[1];
```

可能变成：

```txt
HOLEY_ELEMENTS
```

V8 官方说明，V8 会跟踪数组包含的 elements kind，并基于这个信息优化数组操作。([V8][4])

看这个函数：

```js
function each(array, callback) {
  for (let i = 0; i < array.length; i++) {
    callback(array[i]);
  }
}
```

如果每次传入同一种数组：

```js
each([1, 2, 3], fn);
each([4, 5, 6], fn);
```

`array.length` 和 `array[i]` 的 IC 比较稳定。

但如果：

```js
each([1, 2, 3], fn);           // SMI
each([1.1, 2.2], fn);          // DOUBLE
each(['a', 'b'], fn);          // OBJECT
each([1, , 3], fn);            // HOLEY
```

同一个访问点见到多种 elements kind，就会变 polymorphic。V8 官方在 elements kind 文章中明确举例：同一个 `each` 函数处理不同 elements kind 时，`array.length` 和 `array[index]` 的访问会从 monomorphic 变成 polymorphic，并引入额外检查。([V8][4])

---

# 16. IC miss 是什么？

当 IC 以为会见到某个 Map，但实际来了另一个 Map，就发生 IC miss。

例如：

```js
function getX(o) {
  return o.x;
}

const a = { x: 1, y: 2 };
const b = { x: 2, z: 3 };

getX(a); // IC 记录 MapA
getX(a); // 命中
getX(b); // miss，因为 b.map !== MapA
```

miss 后 V8 会：

```txt
1. 走 fallback / runtime / builtin
2. 找到正确访问路径
3. 更新 IC 状态
4. 可能从 monomorphic 变 polymorphic
5. 如果太复杂，可能变 megamorphic
```

在优化代码里，如果之前生成了强假设，比如：

```txt
这个访问点永远只会见 MapA
```

但后来来了 MapB，可能导致：

```txt
deoptimization
```

也就是从优化代码退回较低层执行。V8 官方 hash table 文章也提到，隐藏类 transition 会导致较差的 polymorphic code，并可能触发 optimized code 的 deoptimization。([V8][5])

---

# 17. IC 与原型链

看代码：

```js
const proto = { x: 1 };
const obj = Object.create(proto);

function getX(o) {
  return o.x;
}

getX(obj);
```

`x` 不在 `obj` 自身，而在原型上。

IC 仍然可以优化，但需要记录更多条件：

```txt
1. obj 的 Map 是否匹配
2. obj 的 prototype 是否还是原来的 proto
3. proto 的 Map 是否匹配
4. proto.x 的位置是否没变
```

如果后续改了原型：

```js
proto.x = 2;
Object.setPrototypeOf(obj, anotherProto);
```

或者增删原型属性，就会破坏之前的假设。

所以性能敏感代码里，通常不建议频繁：

```js
Object.setPrototypeOf(obj, proto);
obj.__proto__ = proto;
动态修改 prototype 方法
```

因为这会让 IC 和优化编译器的假设失效。

---

# 18. IC 与 getter / setter

普通 data property 很容易优化：

```js
const obj = { x: 1 };
obj.x;
```

但 accessor property 更复杂：

```js
const obj = {
  get x() {
    return Math.random();
  }
};

obj.x;
```

此时 `obj.x` 不只是读取字段，而是函数调用：

```txt
Load property
  ↓
发现是 getter
  ↓
调用 getter
```

如果 getter 稳定，V8 也可能优化部分路径，但复杂度明显高于普通字段。

业务建议：

```txt
性能敏感热路径中，不要把高频简单字段访问设计成复杂 getter。
```

尤其是：

```js
class Rect {
  get area() {
    return this.width * this.height;
  }
}
```

如果 `area` 在大循环中频繁访问，要确认它不是隐藏成本来源。

---

# 19. IC 与 Proxy

`Proxy` 对 IC 非常不友好。

```js
const obj = new Proxy(
  { x: 1 },
  {
    get(target, key) {
      return target[key];
    }
  }
);

function getX(o) {
  return o.x;
}

getX(obj);
```

语义上，Proxy 的 `get` trap 可能做任何事情：

```txt
1. 返回动态值
2. 访问远程数据
3. 改变 target
4. 抛异常
5. 触发副作用
```

因此 V8 很难把它当作普通对象字段读取优化。

所以在性能敏感的数据模型里：

```txt
Proxy 适合做开发期响应式、调试、拦截、框架抽象；
不适合放在极高频数值计算、表格大范围遍历、渲染核心循环里。
```

---

# 20. IC 与字典对象 / map-like 对象

有些对象天生不适合 IC：

```js
const dict = {};

for (const key of manyDynamicKeys) {
  dict[key] = value;
}
```

如果 key 高度动态：

```txt
dict.a
dict.b
dict.c
dict.random_123
dict.user_input_key
```

对象可能不断发生 Map transition，甚至进入 dictionary mode。

如果你的语义就是“动态键值表”，更建议用：

```js
const map = new Map();
map.set(key, value);
map.get(key);
```

原因是：

```txt
普通对象更适合稳定结构 record；
Map 更适合动态 key-value dictionary。
```

这和 IC 的优化目标是匹配的：

```txt
稳定 record:
  object + stable Map + IC

动态 dictionary:
  Map / hash table
```

# 21. IC 视角下的最佳实践

## 21.1 保持对象字段稳定

推荐：

```js
class User {
  constructor(name, age) {
    this.name = name;
    this.age = age;
    this.score = 0;
    this.vip = false;
  }
}
```

避免：

```js
class User {
  constructor(name, age, isVip) {
    this.name = name;
    this.age = age;

    if (isVip) {
      this.vip = true;
    }
  }
}
```

核心原因：

```txt
字段稳定
  ↓
Map 稳定
  ↓
IC monomorphic
  ↓
优化编译器更敢生成直接访问代码
```

---

## 21.2 保持属性添加顺序一致

推荐：

```js
function createUser(name, age) {
  return {
    name,
    age,
    score: 0,
  };
}
```

避免同类对象到处拼装：

```js
const u1 = {};
u1.name = 'A';
u1.age = 18;
u1.score = 0;

const u2 = {};
u2.score = 0;
u2.name = 'B';
u2.age = 20;
```

V8 官方明确说明，相同属性、相同顺序的对象共享 HiddenClass。([V8][1])

---

## 21.3 避免热路径 delete

避免：

```js
delete obj.x;
```

推荐：

```js
obj.x = undefined;
```

或者：

```js
obj.x = null;
```

原因：

```txt
delete 可能导致 fast properties → slow/dictionary properties
slow properties 访问更慢
```

V8 官方说明 slow properties 使用自包含字典，属性元信息不再通过 HiddenClass 共享，访问慢于 in-object 和 fast properties。([V8][1])

---

## 21.4 区分 record object 和 dictionary object

适合 object：

```js
const user = {
  id: 1,
  name: 'Alice',
  age: 18,
};
```

适合 Map：

```js
const cache = new Map();

cache.set(dynamicKey, value);
cache.get(dynamicKey);
```

经验判断：

```txt
字段集合固定 → object
字段集合高度动态 → Map
```

---

## 21.5 数组保持 elements kind 稳定

推荐：

```js
const nums = [1, 2, 3, 4];
```

避免：

```js
const arr = [1, 2, 3];
arr.push('x');
arr.push({});
```

推荐数值数组就保持数值数组，字符串数组就保持字符串数组。

避免制造 hole：

```js
delete arr[1];
```

推荐：

```js
arr.splice(1, 1);
```

或者：

```js
arr[1] = undefined;
```

但注意：`undefined` 也可能改变 elements kind，具体取决于数组原始类型和 V8 版本。性能敏感场景要压测。

---

## 21.6 热函数参数类型尽量稳定

避免：

```js
function normalize(input) {
  return input.value;
}

normalize({ value: 1 });
normalize({ value: 2, extra: true });
normalize(new Proxy({ value: 3 }, {}));
normalize(Object.create({ value: 4 }));
```

推荐在外层分流：

```js
function normalizeUser(user) {
  return user.value;
}

function normalizeProxy(proxy) {
  return proxy.value;
}
```

也就是：

```txt
不要让一个热函数承担过多 shape/type 分支。
```

---

## 21.7 不要在热路径动态改 prototype

避免：

```js
Object.setPrototypeOf(obj, proto);
obj.__proto__ = proto;
```

尤其避免在大量对象创建后再改 prototype。

推荐：

```js
class User {
  getName() {
    return this.name;
  }
}
```

或者在对象创建前确定原型结构。

# 22. 一个业务级案例：表格单元格对象设计

假设你做表格，单元格对象如下：

```js
function createCell(value, formula, style) {
  const cell = {};

  cell.value = value;

  if (formula) {
    cell.formula = formula;
  }

  if (style) {
    cell.style = style;
  }

  return cell;
}
```

这在大表格场景里可能非常伤 IC，因为不同 cell 的 shape 很多：

```txt
普通值单元格:
  value

公式单元格:
  value → formula

样式单元格:
  value → style

公式 + 样式:
  value → formula → style
```

更稳定的设计：

```js
function createCell(value, formula, style) {
  return {
    value,
    formula: formula ?? null,
    style: style ?? null,
    type: formula ? 'formula' : 'value',
  };
}
```

这样所有 cell 都是：

```txt
value → formula → style → type
```

热路径：

```js
function renderCell(cell) {
  return cell.value;
}
```

更容易保持 monomorphic 或低 polymorphic。

当然，代价是：

```txt
每个 cell 多存一些空字段
```

所以在表格这种海量对象场景要权衡：

```txt
方案 A：字段补齐，IC 稳定，但内存多
方案 B：字段稀疏，内存少，但 shape 多，IC 差
```

大表格里可以进一步拆分：

```js
// 核心热字段：稳定结构
class CellCore {
  constructor(value, type) {
    this.value = value;
    this.type = type;
  }
}

// 稀疏冷字段：外部 side table
const formulaMap = new Map(); // cellId -> formula
const styleMap = new Map();   // cellId -> style
```

这样可以做到：

```txt
热路径对象 shape 稳定
冷数据放 side table
整体 IC 更友好
```

# 23. 怎么排查 IC 问题？

可以从几个现象判断：

```txt
1. 同一个函数处理过多不同结构对象
2. 热路径里对象字段是条件添加的
3. 有大量 delete
4. 有大量动态 key
5. 数组元素类型混杂
6. 数组从 packed 变 holey
7. 使用 Proxy / getter / setter / prototype mutation
8. 优化后又频繁 deopt
```

V8 官方有 IC 和 Map tracing 基础设施，并且 Indicium 可以把 IC events 和 Map events 关联起来分析，帮助定位真实代码里 Map/IC 如何创建和变化。([V8][3])

如果在本地研究，可以关注这些方向：

```bash
# d8 / Node 的具体参数会随 V8 和 Node 版本变化
# 常见方向是查看 IC log、Map log、deopt log、opt log
```

常见观察指标：

```txt
LoadIC 是否从 monomorphic 变 polymorphic
某个函数是否出现 megamorphic 访问点
Map transition 是否异常多
是否出现 dictionary properties
是否频繁 deopt
```

# 25. 最终关键总结

**Inline Cache 的核心不是缓存值，而是缓存访问路径。**

最重要的链路是：

```txt
JS 动态属性访问
  ↓
V8 观察运行时对象 shape
  ↓
IC 在访问点记录 Map + handler
  ↓
后续 Map 命中则直接 offset load/store
  ↓
Feedback Vector 把这些信息提供给优化编译器
  ↓
Maglev / TurboFan 生成更快的推测性机器码
```

性能排序可以粗略理解为：

```txt
Monomorphic IC
  > Polymorphic IC
  > Megamorphic IC
  > Generic dynamic lookup
```

写 JS 时最重要的 IC 友好原则：

```txt
1. 同类对象字段保持一致
2. 属性添加顺序保持一致
3. constructor 中初始化所有实例字段
4. 热路径避免 delete
5. 动态 key-value 用 Map，不要滥用普通对象
6. 数组元素类型保持稳定
7. 避免 packed 数组变 holey
8. 热函数不要接收过多不同 shape 的对象
9. 谨慎使用 Proxy / getter / 动态 prototype
10. 大规模对象场景中，热字段稳定，冷字段 side table 化
```

一句话收尾：

> **V8 IC 的本质，是用运行时反馈把 JavaScript 的“动态对象访问”尽可能降级成“稳定对象布局下的固定偏移读写”。**
